> **한 줄 요약:** LLM은 원래 **한 토큰씩** 만듭니다(다음 토큰 뽑기의 반복 — temperature 글의 그것). 스트리밍은 특별한 기능이 아니라 **만들어지는 대로 흘려보내는 것**이고, 그 표준 배관이 SSE(Server-Sent Events)예요. 체감 속도는 **첫 토큰까지(TTFT)**가 지배하고, 사고는 대부분 **중간 프록시의 버퍼링**에서 납니다.

## 왜 스트리밍이 자연스러운가

모델은 답을 다 써놓고 보여주는 게 아니라, **토큰 하나 뽑고 → 그걸 입력에 붙여 다음 토큰 뽑고**를 반복합니다. 즉 서버 입장에선 완성본을 기다렸다 주는 쪽이 오히려 **인위적인 지연**이에요. 30초짜리 긴 답변이면 — 논스트리밍은 30초간 빈 화면, 스트리밍은 1초쯤부터 글자가 흐릅니다. 총 시간은 같아도 체감은 하늘과 땅이죠.

그래서 지표도 둘로 나뉩니다.

- **TTFT(첫 토큰까지)** — 사용자가 "반응했다"고 느끼는 순간. 프롬프트 처리 시간이 지배하고, **프롬프트 캐싱이 줄여주는 게 바로 이것**입니다.
- **TPS(초당 토큰)** — 흐르기 시작한 뒤의 속도. 모델 크기·양자화(그 글의 트레이드오프)가 지배.

대시보드에 "응답 시간" 하나만 있다면 반쪽입니다 — 스트리밍 서비스는 TTFT를 따로 재세요.

## SSE의 생김새 — 생각보다 원시적이다

SSE는 그냥 **안 끊는 HTTP 응답**입니다. 헤더 `Content-Type: text/event-stream` 하나 걸고, 본문을 `data:` 줄 단위로 계속 흘려보내는 것.

```
data: {"type":"delta","text":"안녕"}

data: {"type":"delta","text":"하세요"}

data: [DONE]
```

빈 줄이 이벤트 구분자고, 벤더들의 LLM API 스트리밍이 전부 이 형식입니다. WebSocket과 비교하면 — SSE는 **단방향(서버→클라)**이고 그냥 HTTP라 프록시·인증·재시도가 평범하게 동작합니다. "답변을 흘려보내기"에는 양방향이 필요 없으니, LLM 응답 용도로는 SSE가 표준으로 굳었어요.

받는 쪽 뼈대도 단순합니다.

```python
import httpx, json

with httpx.stream("POST", url, json=body, headers=h, timeout=None) as r:
    for line in r.iter_lines():
        if not line.startswith("data: "):
            continue
        payload = line[6:]
        if payload == "[DONE]":
            break
        chunk = json.loads(payload)
        print(chunk_text(chunk), end="", flush=True)   # 오는 대로 흘리기
```

주의 둘 — **타임아웃을 '전체 응답' 기준으로 걸면 안 됩니다**(긴 생성은 몇 분도 정상이니, idle 타임아웃 즉 '다음 청크까지'로). 그리고 줄 파싱은 직접 자르지 말고 가급적 SDK/라이브러리에 맡기세요 — `data:`가 여러 줄로 쪼개지는 등 가장자리 케이스가 있습니다.

## 사고 다발 지점: 중간에 낀 것들이 스트림을 모은다

스트리밍 장애의 전형 — 로컬에선 흐르는데 **운영에 올리면 한참 있다 한 방에 옵니다.** 범인은 거의 항상 중간 계층의 **버퍼링**이에요.

- **nginx 리버스 프록시** — 기본이 응답 버퍼링입니다. 스트리밍 경로에 `proxy_buffering off;` (또는 앱이 `X-Accel-Buffering: no` 헤더로 요청). LLM 게이트웨이 글의 "통과시키며 계측" 원칙이 nginx 설정으로는 이 한 줄입니다.
- **압축** — gzip이 청크를 모아서 압축하려 듭니다. 스트리밍 응답은 압축 제외.
- **LB/CDN** — L7 장비(ALB 글의 그 "뜯어 읽는" 계층)의 idle 타임아웃이 조용한 스트림을 끊습니다. 생성이 길어질 수 있으면 타임아웃 상향 + 주기적 keep-alive 코멘트(`: ping`) 전송이 정석. CDN은 스트리밍 경로를 캐시·버퍼 대상에서 빼고요.
- **직접 만든 게이트웨이** — 응답을 다 모아 검사한 뒤 전달하면 스트리밍이 죽습니다. 청크 단위로 통과시키며 필요한 것(토큰 집계, 마스킹)만 흐름 위에서 처리해야 해요.

증상으로 역추적하면: **한 방에 옴** = 어딘가의 버퍼, **중간에 뚝 끊김** = 어딘가의 idle 타임아웃. curl로 계층을 하나씩 벗겨가며(`curl -N 앱직접` → LB 경유 → 도메인 경유) 어느 층에서 뭉치는지 찾는 것 — 계층 진단 그대로입니다.

## 설계 디테일 둘

**끊김 처리.** 모바일 환경에서 스트림은 자주 끊깁니다. "이어서 생성"은 지원이 제한적이니, 실전은 **재요청 + 이미 받은 부분 활용**(대화 이력에 붙여 "이어서") 또는 짧은 응답 유도. 결제·기록성 작업이라면 스트림 완료 이벤트를 기준으로 확정하는 습관이 필요하고요.

**구조화 출력과의 긴장.** JSON을 스트리밍하면 **중간엔 항상 깨진 JSON**입니다(닫는 괄호가 아직 안 옴). 화면 표시는 텍스트 델타로 하되, 파싱은 완료 후에 — 또는 부분 파싱 지원 라이브러리를 쓰거나, 도구 호출 스트리밍이면 SDK의 누적 파서에 맡기세요. 구조화 출력 글의 사다리가 스트리밍과 만나면 이 한 가지 규칙이 추가되는 셈입니다.

## 한 줄 정리

스트리밍은 **생성의 자연스러운 형태**고, SSE는 그걸 나르는 단순한 HTTP 배관입니다. TTFT를 따로 재고(캐싱이 여길 줄임), **중간 계층의 버퍼·타임아웃**(nginx `proxy_buffering off`, LB idle, gzip 제외)을 청소하고, JSON은 완료 후 파싱 — 글자가 안 흐르면 범인은 모델이 아니라 배관입니다.
