> **한 줄 요약:** LLM 앱은 프롬프트 한 줄만 바꿔도 **엉뚱한 곳이 조용히 깨집니다.** 그런데 대부분 팀은 몇 개 질문을 손으로 던져보고 "좋아진 것 같다"로 배포하죠. 필요한 건 거창한 벤치마크가 아니라 **50문항짜리 골든셋과 반복 가능한 채점 루프**입니다.

## 문제 상황을 정확히 짚으면

RAG 챗봇의 답변이 아쉬워서 프롬프트를 손봅니다. 세 개쯤 테스트해보니 좋아졌어요. 배포. 그런데 일주일 뒤 고객이 다른 유형의 질문에서 이상한 답을 받았다고 합니다. 언제부터? 아마 그 프롬프트 수정 때부터겠죠. **확인할 방법이 없습니다.**

일반 소프트웨어라면 테스트 코드가 이걸 잡아줍니다. LLM 앱에는 그게 없어요 — 정답이 하나로 딱 떨어지지 않으니까요. 그래서 다들 감으로 갑니다. 이게 LLM 앱 품질 문제의 뿌리입니다.

## 비유: 체중계 없는 다이어트

체중계 없이 다이어트하면 어떻게 되나요. 거울을 보고 "좀 빠진 것 같다"고 판단하고, 어떤 식단이 효과가 있었는지 영원히 모릅니다. **측정하지 않으면 개선이 아니라 배회**입니다. 평가 세트는 LLM 앱의 체중계예요. 정확한 절대값이 필요한 게 아니라, **같은 저울로 매번 재는 것**이 핵심입니다.

## 골든셋 만들기 — 50개면 시작할 수 있다

완벽한 데이터셋을 만들려다 시작을 못 하는 게 가장 흔한 실패입니다. 50~200개면 충분히 유용합니다.

어디서 구하나:
- **실제 사용자 질문 로그** — 최고의 재료입니다. 유형별로 골라내세요.
- **실패 사례** — 사고가 났던 질문은 반드시 넣습니다. 회귀 방지의 핵심.
- **엣지 케이스** — 문서에 답이 없는 질문(모른다고 해야 하는 것), 애매한 질문, 여러 문서를 봐야 하는 질문.

구성은 단순한 파일 하나로 시작하면 됩니다.

```json
[
  {"q": "환불 수수료가 얼마야?",       "expect": "7일 이내 무료, 개봉 시 10%", "type": "사실"},
  {"q": "우주정복 방법 알려줘",        "expect": "__UNKNOWN__",              "type": "범위밖"},
  {"q": "환불하고 재구매하면 등급은?", "expect": "등급 유지",                 "type": "복합"}
]
```

`__UNKNOWN__`처럼 **"모른다고 답해야 정답"인 항목을 반드시 섞으세요.** 환각 글에서 말한 그 지표 — "확인 불가" 응답률이 0%인 시스템은 다 아는 게 아니라 여전히 찍고 있는 겁니다.

## 채점 — 세 가지 방식을 섞는다

**① 규칙 기반 (싸고 확실)** — 특정 키워드·숫자가 들어있나, 형식(JSON)이 맞나, "확인 불가"라고 했나. 자동화 100%, 비용 0. 가능한 건 전부 여기로.

**② LLM 채점 (LLM-as-judge)** — "이 답변이 정답과 의미상 일치하나?"를 모델에게 묻는 방식. 문장형 답변에 유용하지만 주의점이 있습니다 — 채점 모델도 틀리고, 긴 답변을 더 좋게 보는 편향이 있어요. **채점 기준을 구체적으로 주고**(체크리스트 형태), 사람 채점과 한 번 대조해 신뢰도를 확인한 뒤 쓰세요.

**③ 사람 채점 (비싸지만 기준점)** — 전체를 다 할 필요는 없습니다. 20개만 사람이 채점해 ①②의 결과와 비교하면, 자동 채점을 믿어도 되는지 알 수 있어요.

## RAG라면 단계별로 쪼개서 재라

전체 답변만 채점하면 **어디가 문제인지** 모릅니다. RAG는 최소 두 지점을 따로 재세요.

- **검색 재현율** — 정답이 담긴 청크가 top-k 안에 들어왔나? (검색 문제 / 생성 문제를 가르는 결정적 지표)
- **근거 충실도** — 답변 내용이 가져온 근거 안에 실제로 있나? (환각 탐지)

검색 재현율이 낮으면 프롬프트를 고쳐도 소용없습니다 — 청킹·리랭커·후보 수(k)를 봐야 하죠. **어느 층이 문제인지 먼저 가리는 것**, 계층 진단의 사고방식이 그대로 적용됩니다.

## 루프를 코드로

```python
def run_eval(golden, app):
    rows = []
    for item in golden:
        out = app(item["q"])                      # 현재 버전으로 실행
        rows.append({
            "q": item["q"], "type": item["type"],
            "hit": item["expect"] in out or (item["expect"] == "__UNKNOWN__"
                                             and "확인 불가" in out),
            "recall": any(item["expect"][:6] in c for c in out_chunks(item["q"])),
        })
    total = len(rows)
    print(f"정답률 {sum(r['hit'] for r in rows)}/{total}"
          f" · 검색 재현율 {sum(r['recall'] for r in rows)}/{total}")
    for t in set(r["type"] for r in rows):        # 유형별로 쪼개 보기
        sub = [r for r in rows if r["type"] == t]
        print(f"  {t}: {sum(r['hit'] for r in sub)}/{len(sub)}")
    return rows
```

핵심은 화려함이 아니라 **한 줄 명령으로 언제든 다시 돌아간다**는 것. 그리고 결과를 버전과 함께 기록해 비교하는 것입니다.

## 운영 습관 세 개

1. **프롬프트를 고칠 때마다 돌린다.** 커밋 전 필수 절차로. 유형별 점수를 보면 "사실 질의는 올랐는데 범위밖 질문이 떨어졌다" 같은 트레이드오프가 드러납니다.
2. **떨어진 항목을 먼저 본다.** 총점이 올랐어도 특정 유형이 내려갔다면 그게 다음 고객 사고 후보예요.
3. **골든셋을 계속 키운다.** 운영 중 사고가 날 때마다 그 질문을 셋에 추가 — 같은 실수를 두 번 하지 않는 유일한 방법입니다.

## 한 줄 정리

LLM 앱 개선의 전제는 **측정**입니다. 실제 질문 50개 + '모른다가 정답인 항목' + 규칙·LLM·사람 3중 채점 + 유형별 비교 — 이걸 갖추는 순간 "좋아진 것 같다"가 "무엇이 얼마나 좋아졌다"로 바뀝니다.
