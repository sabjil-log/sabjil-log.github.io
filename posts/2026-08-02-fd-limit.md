> **한 줄 요약:** 리눅스에서 **소켓, 파이프, 장치까지 전부 '파일'**이고, 프로세스가 열 수 있는 개수에는 한도(기본 1024인 경우가 많음)가 있습니다. 트래픽 좀 받는 서버라면 연결 하나가 fd 하나씩을 먹으니 금방 차요 — 해법은 **한도 올리기 + 누수 잡기** 두 갈래입니다.

[[diagram:fd-limit]]

## 착각부터 교정

"우리 앱은 파일을 몇 개 안 여는데요?" — 파일 디스크립터(fd)는 **열려 있는 모든 입출력 통로의 번호표**입니다.

- 클라이언트 연결 1개 = 소켓 fd 1개
- DB 커넥션 풀 50개 = fd 50개
- 로그 파일, 파이프, 타이머까지 전부 fd

즉 동시 접속 900명 + 커넥션 풀 + 로그 몇 개면, "파일"을 안 열어도 기본 한도 1024는 넘칩니다. 웹서버·프록시·크롤러가 이 에러의 단골인 이유예요.

## 한도는 3층 구조다

여기가 헷갈리는 지점입니다 — 올렸는데 안 먹는다면 **다른 층**을 올린 겁니다.

```bash
# ① 시스템 전체 한도 (커널)
cat /proc/sys/fs/file-max

# ② 내 셸/프로세스의 한도 (ulimit)
ulimit -n                      # soft (실제 적용값)
ulimit -Hn                     # hard (soft를 올릴 수 있는 상한)

# ③ 이미 떠 있는 그 프로세스의 진짜 한도 ← 제일 중요
cat /proc/$(pgrep -f myapp)/limits | grep "open files"
```

③이 핵심입니다. **한도는 프로세스가 시작될 때 물려받는 값**이라, 지금 셸에서 `ulimit -n 65535`를 쳐도 이미 떠 있는 서비스에는 아무 효과가 없어요. 그리고 —

**systemd로 뜨는 서비스는 ulimit 설정 파일(/etc/security/limits.conf)을 아예 안 봅니다.** limits.conf는 로그인 세션용이거든요. 서비스는 유닛에서 직접 지정합니다:

```ini
# systemctl edit myapp  →  override에 추가
[Service]
LimitNOFILE=65535
```

```bash
sudo systemctl daemon-reload && sudo systemctl restart myapp
cat /proc/$(pgrep -f myapp)/limits | grep open    # 반영 확인까지가 한 세트
```

"limits.conf 고쳤는데 안 돼요"의 답이 십중팔구 이겁니다 — journalctl 글에서 본 그 원칙: 서비스의 세계는 systemd가 지배합니다.

## 올리기 전에: 정상 사용인가, 누수인가

한도 상향은 **정상적으로 많이 쓰는 경우**의 처방입니다. 그런데 fd 사용량이 시간이 갈수록 **우상향**한다면 — 그건 닫지 않는 코드, 즉 **누수**고, 한도를 올려봐야 죽는 날짜만 미뤄집니다. OOM 글의 그 구분(스파이크냐 우상향이냐)과 똑같은 판별법이에요.

```bash
# 지금 누가 많이 열고 있나 — fd 개수 랭킹
for p in /proc/[0-9]*; do echo "$(ls $p/fd 2>/dev/null | wc -l) $(cat $p/comm 2>/dev/null)"; done | sort -rn | head

# 그 프로세스가 '뭘' 열어두고 있나
ls -l /proc/12345/fd | head -20
sudo lsof -p 12345 | awk '{print $5}' | sort | uniq -c | sort -rn
#   1800 sock   ← 소켓이 압도적이면 연결을 안 닫는 것
#     12 REG    ← 일반 파일
```

`sock`이 계속 늘면 응답 후 연결을 안 닫는 코드나 **CLOSE_WAIT 방치**(상대는 끊었는데 우리 앱이 close()를 안 부른 상태)를 의심하세요. `ss -tan | grep CLOSE-WAIT | wc -l` 이 계속 늘고 있다면 확정입니다. 파일이라면 `with open(...)` 없이 열고 버리는 루프가 단골이고요.

## 처방 정리

1. **누수면 코드 수정이 답** — close 누락, 커넥션 풀 미사용(그 TIME_WAIT 글의 keep-alive 얘기가 fd에도 그대로), CLOSE_WAIT 방치.
2. **정상 사용량이면 한도 상향** — systemd 서비스는 `LimitNOFILE=`, 컨테이너는 도커/쿠버 쪽 ulimit 옵션. 요즘 서버라면 65535는 부담 없는 값입니다.
3. **모니터링에 fd 사용률 추가** — `현재 fd 수 / 한도` 를 80%에서 알람. 이 지표가 있으면 이 에러를 두 번 다시 새벽에 만나지 않습니다.

## 한 줄 정리

"파일"은 소켓 포함이고, 한도는 **떠 있는 프로세스 기준(/proc/PID/limits)**으로 확인하며, systemd 서비스는 **LimitNOFILE**로 올립니다. 단, 우상향 그래프면 한도가 아니라 **누수** — lsof로 sock/REG 비율부터 보세요.
