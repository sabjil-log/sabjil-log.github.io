> **한 줄 요약:** 새 인스턴스는 **부팅 → 앱 기동 → 의존성 연결 → 캐시 예열**을 거쳐야 정상 응답을 냅니다. 이 시간을 안 주면 LB 헬스체크가 "죽었다"고 판정해 **교체 → 또 교체**의 루프가 돌고, 트래픽은 준비 안 된 서버로 쏟아지죠. 처방은 두 다이얼 — **헬스체크 그레이스 기간**과 **워밍업(예열) 시간**입니다.

[[diagram:warmup-grace]]

## 증상

트래픽이 늘어 오토스케일링이 2대를 추가했습니다. 그런데 —

```
09:01  인스턴스 i-A 시작
09:02  헬스체크 실패 (3회 연속) → Unhealthy → 종료
09:03  대체 인스턴스 i-B 시작
09:04  또 실패 → 종료 → i-C 시작 ...
```

스케일링 이력에 "시작·종료"가 번갈아 찍히고, 기존 서버들은 여전히 과부하. 확장이 **비용만 쓰고 용량은 안 늘리는** 상태입니다. 오토스케일링 글의 사각지대와 다른 축의 실패 — 거기가 "안 줄어드는" 문제였다면, 여기는 "늘어도 소용없는" 문제죠.

## 원인: 준비에도 시간이 든다

새 서버가 트래픽을 제대로 받기까지의 단계를 시간축에 놓으면:

```
0s     인스턴스 시작 (OS 부팅)
~40s   초기화 스크립트 (패키지·설정·시크릿 가져오기)
~70s   앱 프로세스 기동 (JVM 워밍업, 의존성 로드)
~90s   DB·캐시 연결, 헬스 엔드포인트 200 시작
~150s  JIT·로컬 캐시 예열 — 응답 지연이 정상 수준으로
```

헬스체크가 **30초 간격 × 3회 실패 = 90초**에 판정하면, 아직 앱이 안 뜬 70초 시점의 실패를 세다가 죽여버립니다. 그리고 헬스체크를 통과한 90초부터 트래픽이 들어오는데, 150초까지는 **느린 상태** — p95가 확장할 때마다 튀는 이유(알람 설계 글의 그 p95).

## 다이얼 ① — 헬스체크 그레이스 기간

"시작 후 N초 동안은 헬스체크 실패를 세지 않는다." 오토스케일링 그룹 설정에 있는 **health check grace period**(NCP도 대응 설정)가 이것입니다.

```
그레이스 = (앱이 헬스 200을 내기까지 실제 시간) × 1.5 정도
```

실측이 전제입니다 — 인스턴스를 하나 띄우고 `curl` 루프로 첫 200까지 몇 초인지 재세요. 감으로 300초를 주면 진짜 죽은 서버를 5분간 못 알아채니, 넉넉히가 아니라 **실측 × 여유**가 정답입니다.

헬스체크 자체도 점검 대상입니다(헬스체크 3대장 글) — 특히 **경로.** `/`가 무거운 페이지면 부팅 직후 타임아웃이 잦고, 반대로 `/health`가 "프로세스 살아있음"만 답하면 DB 연결 전에 200을 내서 트래픽이 너무 일찍 옵니다. **의존성까지 확인하는 readiness 성격의 엔드포인트**가 맞습니다 — 쿠버의 readiness 프로브가 정확히 이 구분을 제도화한 것이고요.

## 다이얼 ② — 워밍업(예열) 시간

헬스 200이 나와도 성능이 정상까지 오는 데 시간이 더 걸립니다. 두 가지 처방:

- **스케일링 계산에서의 워밍업** — "새 인스턴스는 N초 동안 집계 지표에 포함하지 않는다". 안 그러면 새 서버의 낮은 CPU가 평균을 끌어내려 **확장 직후 축소 판정**이 나는 진동이 생깁니다(사각지대 글의 그 임계값 문제가 시간축으로 재현).
- **LB 단계적 트래픽 유입(slow start)** — 새 대상에 처음엔 트래픽을 조금만 주고 수 분에 걸쳐 늘리는 LB 기능. JVM류나 로컬 캐시 의존 앱에 특효.

## 근본: 준비 시간 자체를 줄이기

다이얼로 견디는 것과 별개로, 부팅 시간 자체가 짧으면 모든 게 편해집니다.

- **골든 이미지** — 스냅샷/이미지 글의 그 방식. 부팅 후 패키지 설치를 하는 대신, 다 깔린 이미지로 시작. 초기화 40초 → 5초.
- **의존성 대기 로직** — 앱이 DB 연결 실패로 죽어 재시작 루프를 도는 대신, 연결까지 재시도하며 기다리기(systemd 글의 Restart 설계와 연결).
- **컨테이너라면** — 이미지 다이어트(멀티스테이지)로 pull 시간 단축, requests/limits 글의 리소스 보장으로 기동 시 CPU 스로틀링 방지. 쿠버에선 `startupProbe`가 그레이스 기간의 역할입니다.

## 점검 체크리스트

```
□ 새 인스턴스 첫 200까지 시간 실측 → 그레이스 = 그 × 1.5
□ 헬스 경로가 의존성(DB·캐시)까지 확인하는가
□ 스케일링 지표 집계에 워밍업 제외 설정
□ LB slow start 지원 여부 확인·적용
□ 스케일링 이력에서 "시작 후 N분 내 종료" 패턴 검색 (있으면 이 문제 진행 중)
□ 골든 이미지로 초기화 단계 제거
```

## 한 줄 정리

새 서버에게 **준비 시간을 안 주면 확장이 교체 루프가 됩니다.** 그레이스는 실측×1.5, 헬스 경로는 의존성까지, 스케일링 계산에 워밍업 제외, LB는 slow start — 그리고 골든 이미지로 준비 시간 자체를 줄이는 것이 근본입니다.
