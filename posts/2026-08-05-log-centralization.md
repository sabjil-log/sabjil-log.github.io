> **한 줄 요약:** 서버를 소모품(이미지에서 다시 태어나는 소)으로 만들었다면 필연적으로 따라오는 숙제 — **로그가 서버 로컬에 있으면 서버와 함께 증발합니다.** 답은 구조 하나예요: **각 서버의 수집기 → 중앙 저장소 → 검색·알람 + 보존 정책.**

## 왜 이제는 필수인가

전통적 디버깅: 서버에 SSH로 들어가 `journalctl`과 `grep`으로 수사(그 글들의 방식). 이 방식이 무너지는 순간이 셋 있습니다.

1. **서버가 사라질 때** — 오토스케일링이 축소하면서 지운 서버, 이미지에서 재생성한 서버(스냅샷 글의 그 소모품 철학). 장애 원인이 담긴 로그가 서버와 함께 화장됩니다.
2. **서버가 여러 대일 때** — 요청 하나가 LB를 거쳐 10대 중 어디로 갔는지 모른 채, 10대에 순서대로 들어가 grep하는 건 수사가 아니라 고행입니다.
3. **서버가 뚫렸을 때** — 침입자가 제일 먼저 지우는 게 로컬 로그입니다. **서버 밖으로 이미 나간 로그**만이 증거로 남아요(보안 관점에서 중앙화는 백업이 아니라 증거 보전입니다).

## 기본 구조 — 우체국 모델

```
[각 서버] 앱은 stdout/파일에 쓰기만 → [수집기(에이전트)]가 부치고 → [중앙 저장소] → 검색·대시보드·알람
```

역할 분리가 핵심입니다.

- **앱은 로그를 '보내지' 않습니다.** stdout이나 파일에 쓰기만 — 전송 실패·재시도·버퍼링은 앱의 일이 아니에요. (앱에서 직접 외부 로그 API를 호출하는 설계는 로그 시스템 장애가 앱 장애로 번지는 지름길입니다.)
- **수집기(Fluent Bit, Vector 등)**가 각 서버에서 파일을 꼬리물기(tail)해 중앙으로 부칩니다. 네트워크 단절 시 로컬 버퍼로 버티다 재전송 — 우체국의 일이죠.
- **중앙 저장소**는 관리형이 기본값입니다 — NCP Cloud Log Analytics, AWS CloudWatch Logs 계열. 검색·보존·권한이 딸려오고, 로그 시스템 자체를 운영하는 일(그것도 만만치 않은 인프라)을 삽니다. 자체 구축(OpenSearch 스택 등)은 볼륨이 커져 관리형 요금이 아플 때의 다음 단계로.

컨테이너/쿠버라면 이 구조가 반쯤 강제됩니다 — 컨테이너는 stdout으로 쓰고, 노드의 수집기(DaemonSet)가 걷어가는 표준 패턴. docker 볼륨 글에서 "컨테이너는 버려질 수 있다"고 한 그 전제가 로그에도 그대로 적용되는 거예요.

## 실무를 가르는 세 가지 결정

**① 형식: 처음부터 JSON 한 줄로.** `2026-08-05 ERROR 결제 실패 user=123` 같은 자유 문장은 중앙에서 파싱 지옥을 만듭니다(구조화 출력 글의 교훈이 로그에도). 앱에서부터 **한 줄 JSON**으로 —

```json
{"ts":"2026-08-05T14:30:00+09:00","level":"error","msg":"payment failed","user_id":123,"order_id":"A-9","trace_id":"7f3a..."}
```

**trace_id(요청 ID)**가 백미입니다 — LB 뒤 10대 문제를 "이 요청의 전체 여정"으로 꿰는 열쇠. 게이트웨이/LB에서 요청 ID를 발급해 헤더로 흘리고 모든 로그에 찍게 하세요.

**② 보존: 뜨거움/차가움 분리.** 전부 검색 가능한 상태로 쌓으면 로그가 비용 누수 톱6이 됩니다(그 글에 추가할 판). 정석은 계층화 —

```
최근 7~30일: 중앙 저장소 (검색 가능, 비쌈)
그 이후:     Object Storage로 내보내기 (싸고, 필요시 재적재)
법정 보존:   요구 기간만큼 콜드에 (컴플라이언스 확인)
```

**③ 수집 범위: 앱 로그만이 아니다.** 시스템 로그(journald), 웹서버 액세스 로그, **그리고 감사 추적**(누가 SSH 접속했나 — 배스천 글의 그 로그, 클라우드 API 호출 이력)까지. 특히 감사 로그는 "서버 밖 보전"의 가치가 가장 큰 대상입니다.

## 흔한 함정

- **민감정보 유입** — 비밀번호·토큰·주민번호가 로그에 찍혀 중앙으로 모이면, 로그 시스템이 **회사에서 제일 큰 개인정보 저장소**가 됩니다. 앱 단에서 마스킹이 1선, 수집기 필터가 2선.
- **수집기 자원 무한정** — 수집기의 버퍼가 디스크를 다 먹거나(디스크 알람의 단골 범인) CPU를 잡아먹는 사고. 버퍼 상한과 수집기 자체 모니터링을 잊지 마세요.
- **debug 레벨 전송** — 대역폭·저장 비용이 곱으로 뜁니다. 중앙 전송은 info 이상, debug는 로컬 단기 보관이 일반적 균형.
- **시계 불일치** — 서버들의 시간이 어긋나면 중앙에서 타임라인이 뒤섞입니다. NTP 동기화(그리고 로그의 타임존 명시 — cron UTC 글의 그 교훈)가 전제 조건.

## 한 줄 정리

로그 중앙화는 **"서버는 죽어도 로그는 남는다"**를 구조로 보장하는 일입니다. 앱은 JSON 한 줄로 쓰기만, 수집기가 부치고, 관리형 저장소에서 찾고, 뜨거움/차가움으로 보존을 계층화 — 그리고 trace_id 하나가 열 대의 서버를 한 편의 이야기로 만들어줍니다.
