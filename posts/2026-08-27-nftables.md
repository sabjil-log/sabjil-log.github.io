> **한 줄 요약:** nftables는 iptables의 후계입니다. 지금 배포판에서 `iptables` 명령이 먹혀도 대개 **뒤에서 nftables로 번역**되고 있어요. 구조는 단순합니다 — **table(주소패밀리별 서랍) → chain(훅에 걸린 규칙 묶음) → rule** 3층이고, `nft list ruleset` 한 줄이면 전체가 보입니다.

[[diagram:nftables-tree]]

## 왜 알아야 하나

서버에서 통신이 안 될 때, 계층 진단의 5번 칸(방화벽)에는 세 겹이 있습니다 — 클라우드 ACG/NACL, 그리고 **OS 내부 방화벽**. ACG를 아무리 열어도 OS 안에서 DROP하고 있으면 tcpdump 패턴 ③(SYN만 반복)이 나오죠. 그 OS 내부 방화벽의 현재 표준이 nftables입니다.

혼란의 원인 하나 짚고 가면 — `iptables -L`이 아무것도 안 보여주는데 통신이 막히는 경우가 있습니다. 규칙이 nftables 쪽에 직접 작성돼 있고(firewalld나 도커, 또는 관리자가), 호환 계층이 그걸 못 보여주는 상황이에요. **`nft list ruleset`이 진실**입니다.

## 구조: 3층

```
table inet filter {            ← 서랍: 주소 패밀리(inet=IPv4+6) + 이름
  chain input {                ← 묶음: 어느 훅에, 우선순위, 기본 정책
    type filter hook input priority 0; policy drop;
    ct state established,related accept       ← 규칙들
    iifname "lo" accept
    tcp dport { 22, 80, 443 } accept
  }
  chain forward { ... }
  chain output  { ... }
}
```

iptables와 결정적으로 다른 점 둘:

- **테이블·체인을 내가 만듭니다.** iptables는 filter/nat 등 고정 테이블에 규칙을 얹었지만, nftables는 서랍부터 정의해요. 그래서 여러 프로그램(firewalld, docker, k8s)이 **각자의 테이블**을 갖고 공존합니다 — 규칙이 안 보이던 이유가 대개 이것.
- **집합(set) 문법.** `{ 22, 80, 443 }` 처럼 한 줄로 묶고, 이름 붙인 집합·맵도 만듭니다. iptables에서 포트마다 규칙을 늘어놓던 것이 한 줄로 줄어요.

`ct state established,related accept` 한 줄도 짚어둘 만합니다 — 연결 추적으로 **응답 트래픽을 자동 허용**하는 규칙, 즉 ACG 글의 그 "스테이트풀"을 OS에서 구현하는 문장입니다. 이 줄이 없으면 NACL 글의 임시 포트 함정이 서버 안에서 재현됩니다.

## 읽기 위한 명령 넷

```bash
sudo nft list ruleset                 # 전체 — 진실은 여기
sudo nft list table inet filter       # 특정 서랍만
sudo nft -a list ruleset              # handle 번호 표시 (삭제할 때 필요)
sudo nft monitor trace                # (트레이스 켠 뒤) 패킷이 어느 규칙에 걸리나 실시간
```

디버깅의 핵심은 **순서**입니다 — 체인 안에서 위에서 아래로 평가되고, `accept`/`drop`을 만나면 종료. NACL 글에서 본 "번호 순서" 함정이 여기서도 같아요: 위쪽의 넓은 규칙이 아래쪽 의도를 무력화합니다. 그리고 `policy drop`인 체인은 **아무 규칙에도 안 걸리면 버림**이니, 새 서비스 포트를 여는 걸 잊으면 조용히 막힙니다.

카운터를 붙이면 "이 규칙이 실제로 걸리고 있나"를 숫자로 볼 수 있습니다.

```bash
sudo nft add rule inet filter input tcp dport 8080 counter accept
sudo nft list ruleset | grep -A1 8080      # packets/bytes 증가 확인
```

## 최소한의 쓰기

```bash
# 임시로 포트 열기 (재부팅하면 사라짐 — 그게 안전판)
sudo nft add rule inet filter input tcp dport 8080 accept

# 방금 규칙 지우기: handle 확인 후
sudo nft -a list chain inet filter input | grep 8080     # handle 42
sudo nft delete rule inet filter input handle 42

# 영구 반영은 배포판 방식대로 (/etc/nftables.conf + systemctl enable nftables,
# 또는 firewalld/ufw를 쓰는 서버라면 그 도구로 — 직접 nft로 쓰면 덮어써집니다)
```

마지막 괄호가 실무에서 제일 중요합니다. **관리 도구가 있는 서버에 nft로 직접 쓰면 충돌**합니다 — firewalld가 리로드할 때 내 규칙이 사라지고, 왜 사라졌는지 몰라 한참 헤매게 되죠. 서버에 firewalld/ufw가 도는지 먼저 확인하고, 있으면 그 도구의 문법으로 여세요.

## 도커와의 관계

도커는 자기 테이블/체인을 만들어 포트 공개(`-p`)와 NAT을 처리합니다. 그래서 — **도커로 공개한 포트는 내 input 체인 규칙을 우회하는 것처럼 보입니다**(실제로는 다른 훅·체인에서 처리). "방화벽에서 막았는데 컨테이너 포트가 열려 있다"는 유명한 함정이고, 해결은 도커 쪽 설정(포트를 127.0.0.1에만 바인딩하거나, 도커의 iptables 통합 옵션 조정)입니다. docker-localhost 글의 그 "주소 체계가 다르다"는 감각이 방화벽에도 적용되는 셈이에요.

## 한 줄 정리

**`nft list ruleset`이 진실**이고, 구조는 table → chain(훅·policy) → rule, 평가는 위에서 아래. `ct state established` 한 줄이 스테이트풀을 만들고, `policy drop` 체인은 누락된 포트를 조용히 막습니다. 그리고 firewalld·도커가 도는 서버에서는 **직접 쓰지 말고 그 도구로** — 충돌이 미스터리의 원천입니다.
