> **한 줄 요약:** **스냅샷은 디스크 한 장의 특정 시점**, **이미지(AMI/서버 이미지)는 부팅 가능한 서버 한 대의 묶음**입니다. "데이터를 어제로 되돌리고 싶다"는 스냅샷, "이 서버와 똑같은 걸 한 대 더/다시 만들고 싶다"는 이미지 — **복구 시나리오가 곧 선택 기준**이에요.

## 헷갈리는 이유

콘솔에 "스냅샷 생성"과 "이미지 생성"이 나란히 있고, 둘 다 "백업"처럼 보입니다. 실제로 이미지는 내부적으로 스냅샷을 포함하기도 해서 경계가 더 흐릿하죠. 하지만 **찍는 대상**이 다릅니다.

- **스냅샷** = **디스크(볼륨) 한 장**의 시점 사본. 사진으로 치면 서랍 속 내용물 촬영.
- **이미지** = **서버 전체 구성**의 사본 — OS가 깔린 루트 디스크(+ 부속 정보)를 묶어 "이걸로 새 서버를 부팅할 수 있는" 형태. 집 전체를 통째로 본뜬 모형.

## 시나리오로 가르기

**"데이터가 망가졌다, 어제로 돌리고 싶다"** → **스냅샷.** DB 볼륨, 업로드 파일 볼륨처럼 **내용이 계속 변하는 디스크**는 주기적 스냅샷이 답입니다. 복구는 스냅샷에서 새 볼륨을 만들어 갈아 끼우는 방식 — 관리형 DB 글에서 본 "복구는 새로 만드는 것"과 같은 문법이죠.

**"서버가 통째로 날아갔다 / 똑같은 서버가 더 필요하다"** → **이미지.** OS 설정, 설치한 패키지, 배포된 앱까지 굳힌 **부팅 가능한 원판**이라, 장애 복구·오토스케일링의 시작 템플릿·배스천 재생성("부수고 다시 만들 수 있는 빈 껍데기"의 전제)이 전부 이미지 기반입니다.

교차 사용이 안 되는 게 아니라 **비효율**인 겁니다 — 이미지로 데이터를 백업하면 매번 OS까지 통째로 찍는 낭비고, 스냅샷만으로 서버를 복구하려면 볼륨에서 부팅 구성을 손으로 재조립해야 하죠.

## 실전 조합: 소 = 이미지, 우유 = 스냅샷

정석 구성은 역할 분리입니다.

```
서버(소):    앱·OS 구성 → 이미지로 관리 (배포·버전 단위로 갱신)
데이터(우유): DB·업로드 볼륨 → 스냅샷으로 관리 (매일 + 보존 정책)
```

이렇게 나누면 서버는 **언제든 이미지에서 다시 태어나는 소모품**(도커 볼륨 글의 그 철학의 VM 버전)이 되고, 지켜야 할 것은 데이터 볼륨 하나로 좁혀집니다. 복구 훈련도 단순해져요 — 이미지로 새 서버 → 최신 스냅샷 볼륨 부착 → 끝.

## 함정 넷

**① 실행 중 스냅샷의 정합성.** 스냅샷은 "그 순간"을 찍지만, DB가 메모리에 들고 있던 쓰기 중 데이터까지 찍지는 못합니다. 파일시스템은 대개 크래시 복구가 되지만, **DB 볼륨은 가능하면 정지점을 만들고**(잠깐 쓰기 멈춤, 또는 DB 자체 백업과 병행) 찍는 게 안전합니다. 관리형 DB의 자동 백업이 이 문제를 대신 풀어주는 것이고요.

**② 첫 이미지 갱신을 잊는 것.** 서버를 세팅하고 이미지를 떠둔 뒤 반 년간 패치·설정 변경을 서버에만 반영 — 장애 날에 복구해보니 반 년 전 서버가 태어납니다. **이미지에도 버전과 갱신 주기**가 필요해요 (배포 파이프라인에서 이미지를 굽는 "골든 이미지" 방식이 이것의 자동화).

**③ 보존 정책 없는 자동화.** 비용 누수 글의 그 2번 항목 — 스냅샷은 증분이라 하나하나는 싸 보여도, 무기한 쌓이면 원본보다 비쌉니다. 일7+주4+월3 같은 정책을 자동화에 반드시 짝지으세요.

**④ 같은 계정·리전에만 두는 것.** 스냅샷·이미지가 원본과 같은 장애 반경 안에 있으면 "백업"의 절반만 한 겁니다. 중요한 것은 **다른 리전으로 복제**(리전·AZ 글의 ③단계 대응이 바로 이 지점) — 계정 탈취까지 고려하면 별도 계정 보관이 다음 단계입니다.

## 확인 명령

```bash
# 내 스냅샷들 — 언제 것까지 있고 얼마나 쌓였나 (AWS 예)
aws ec2 describe-snapshots --owner-ids self \
  --query 'Snapshots[].[SnapshotId,VolumeId,StartTime,VolumeSize]' --output table | head

# 이미지 최신본이 언제인지 — 반 년 전이면 ②번 함정 진행 중
aws ec2 describe-images --owners self \
  --query 'Images[].[ImageId,Name,CreationDate]' --output table
```

NCP도 서버 이미지/스냅샷 메뉴에서 같은 점검이 됩니다 — **생성일 컬럼**이 곧 건강 지표예요.

## 한 줄 정리

**디스크의 시점 = 스냅샷, 부팅 가능한 서버의 원판 = 이미지.** 소(서버)는 이미지로 언제든 다시 만들고, 우유(데이터)는 스냅샷으로 매일 지키되 — 보존 정책, 이미지 갱신 주기, 타 리전 복제까지가 "백업했다"의 완성형입니다.
