> **한 줄 요약:** 벡터 검색은 **뜻이 비슷한 것**을 찾고, 키워드 검색(BM25)은 **글자가 정확히 일치하는 것**을 찾습니다. RAG에서 못 찾는 사례의 상당수가 후자 유형(제품 코드, 에러 번호, 고유명사)이라 — **둘을 함께 돌려 결과를 합치는 하이브리드**가 리랭커보다 먼저 손볼 카드일 수 있습니다.

## 벡터 검색이 약한 지점

코사인 유사도 글에서 봤듯 임베딩은 **의미의 방향**을 봅니다. 그래서 "환불 규정"과 "반품 절차"를 잘 연결하죠. 그런데 바로 그 성질 때문에 약한 유형이 있습니다.

- **정확한 식별자** — "ERR-4711 에러 원인?" → 임베딩에서 ERR-4711과 ERR-4712는 거의 같은 벡터입니다. 엉뚱한 에러 문서가 올라옵니다.
- **드문 고유명사** — 사내 시스템명, 고객사명, 제품 코드. 학습에 거의 없던 토큰이라(토큰 글의 그 쪼개짐) 벡터가 흐릿합니다.
- **숫자·버전** — "v2.3.1에서 바뀐 것" → 2.3.1과 2.4.0의 구분이 약합니다.
- **짧은 질의** — 단어 한두 개는 문맥이 없어 벡터가 방향을 못 잡습니다.

반대로 BM25(키워드 통계 기반 검색)는 이 유형에 강합니다 — **드문 단어에 높은 가중치**를 주는 게 원리라, ERR-4711이 들어간 문서를 정확히 집어내죠. 대신 "환불"로 검색하면 "반품"만 적힌 문서를 못 찾습니다.

**즉 둘의 약점이 정확히 상보적**입니다. 그래서 합치는 게 자연스러운 결론이에요.

## 합치는 방법 — RRF가 무난한 기본값

두 검색 결과를 어떻게 하나로 만드느냐가 문제입니다. 점수를 직접 더하는 건 위험합니다 — BM25 점수(0~수십)와 코사인 유사도(0~1)는 **스케일이 다르고** 질의마다 분포도 달라서요.

실무 기본값은 **RRF(Reciprocal Rank Fusion)** — 점수 대신 **순위**만 씁니다.

```python
def rrf(rank_lists, k=60):
    scores = {}
    for ranked in rank_lists:                 # [벡터 결과, BM25 결과]
        for i, doc_id in enumerate(ranked):   # i = 0-based 순위
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + i + 1)
    return sorted(scores, key=scores.get, reverse=True)

final = rrf([vector_top50, bm25_top50])[:20]   # 합친 상위 20개를 리랭커로
```

점수 스케일 문제를 순위로 우회하는 게 요점이고, **양쪽에서 모두 상위인 문서가 자연스럽게 올라옵니다.** k는 완만함 조절 다이얼(60이 관례적 기본값)이고, 한쪽을 더 신뢰하고 싶으면 리스트별 가중치를 주는 변형도 씁니다.

## 파이프라인에서의 위치

RAG 2단 검색(리랭커 글)이 3단이 됩니다.

```
질의 ─┬─ 벡터 검색  top-50 ─┐
      └─ BM25 검색  top-50 ─┴─ RRF 융합 → top-20 → 리랭커 → top-5 → LLM
```

주의: 1차 후보를 합치는 것이니 **각 검색의 k는 넉넉히**(각 50 정도) 가져와야 융합의 이득이 납니다. 그리고 리랭커가 뒤에 있으면 융합 결과의 순서가 다소 거칠어도 무해합니다 — 리랭커가 정예를 다시 줄 세우니까요.

## 한국어에서 신경 쓸 것

BM25는 **토크나이저에 크게 의존**합니다. 한국어는 조사·어미가 붙어 "환불을"과 "환불이"가 다른 토큰이 되니, 형태소 분석기(nori, mecab류)를 붙이지 않으면 키워드 검색 품질이 급락합니다. Elasticsearch/OpenSearch를 쓰면 nori 플러그인이 표준 선택이고, 경량 구현이면 형태소 분석 + 불용어 처리 정도는 넣어야 합니다.

반대로 **식별자·코드는 형태소 분석을 타면 안 됩니다** — ERR-4711이 쪼개지면 의미가 없어지니, 그런 필드는 별도로(정확 일치용 필드로) 인덱싱하는 구성이 실전에서 잘 먹힙니다.

## 도입 판단 — 언제 이걸 먼저 하나

평가 글의 검색 재현율이 낮을 때, 손볼 순서는 상황에 따라 다릅니다.

```
실패 사례를 열어보고 —
· 동의어·표현 차이로 못 찾음      → 임베딩 모델 교체 / 청킹 조정
· 코드·번호·고유명사로 못 찾음    → 하이브리드 (BM25 추가) ★
· 후보엔 있는데 순위가 밀림        → 리랭커
· 정답 문서 자체가 인덱스에 없음   → 인덱싱 파이프라인 (캐시 글의 삭제 처리 등)
```

**실패 사례를 유형별로 세어보는 것**이 결정을 만듭니다. 감으로 리랭커부터 붙이면, 식별자 검색 실패는 그대로 남습니다.

## 한 줄 정리

벡터는 **뜻**, BM25는 **글자** — RAG의 못 찾는 사례를 열어보면 후자 유형이 꽤 많습니다. 두 검색을 각각 넉넉히 돌려 **RRF로 순위 융합**하고 리랭커로 넘기세요. 한국어는 형태소 분석기가 전제이고, 식별자 필드는 쪼개지 않는 것 — 이 두 가지만 챙기면 하이브리드는 가성비 좋은 개선입니다.
