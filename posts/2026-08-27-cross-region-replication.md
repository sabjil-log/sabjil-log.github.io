> **한 줄 요약:** 백업의 가치는 **원본과 얼마나 독립적인가**로 정해집니다. 같은 리전이면 리전 장애에 함께 죽고, 같은 계정이면 계정 탈취·실수 삭제에 함께 지워집니다. 그래서 진짜 백업은 **다른 리전 + 다른 권한 경계 + 되돌릴 수 없는 보존**이에요.

## 사고 시나리오로 보는 독립성

리전·AZ 글에서 장애 반경을 3단계로 봤습니다. 백업을 그 반경 위에 놓아보면 —

| 사고 | 같은 AZ 백업 | 같은 리전 다른 AZ | 다른 리전 | 다른 계정 |
|---|---|---|---|---|
| 볼륨 손상·실수 삭제 | ✓ 살아남음 | ✓ | ✓ | ✓ |
| AZ 장애 | ✕ 함께 죽음 | ✓ | ✓ | ✓ |
| 리전 장애 | ✕ | ✕ | ✓ | ✓ |
| 계정 탈취·권한 오용 | ✕ | ✕ | ✕(같은 계정) | ✓ |
| 랜섬웨어(원본 암호화) | 스냅샷이 남아 있으면 ✓ | ✓ | ✓ | ✓(가장 안전) |

표의 마지막 두 줄이 최근 설계가 바뀐 이유입니다. 리전 장애는 드물지만, **권한 사고와 랜섬웨어는 드물지 않습니다.** 그래서 "다른 리전"에서 멈추지 않고 "다른 계정 + 삭제 불가 보존"까지 가는 게 요즘 기준이에요.

## 세 가지 분리

**① 지리적 분리 (다른 리전).** Object Storage의 리전 간 복제 기능, 스냅샷·이미지의 타 리전 복사(스냅샷 글의 그 함정 ④), DB의 크로스 리전 백업. 대개 **복제 트래픽에 전송 요금**이 붙으니(비용 누수 글의 그 화살표) 대상을 골라야 합니다 — 전부가 아니라 **없으면 사업이 멈추는 것**만.

**② 권한 분리 (다른 계정/프로젝트).** 운영 계정의 자격증명이 유출되거나 오용돼도 백업 계정은 못 건드리게. 구현은 "백업 계정이 운영 계정에서 **끌어오기(pull)**"가 정석입니다 — 운영 쪽에 백업 계정 쓰기 권한을 주는 push 방식은 유출 시 백업까지 뚫리니까요.

**③ 시간적 분리 (되돌릴 수 없는 보존).** 오브젝트 락·불변 보존 기능으로 **보존 기간 내 삭제·변경 자체를 금지**. 관리자 권한으로도 못 지우는 상태를 만드는 것 — 랜섬웨어와 내부자 실수 양쪽에 대한 마지막 방어선입니다.

## 얼마나 자주, 얼마나 오래 — RPO/RTO로 정하기

용어 두 개면 대화가 정확해집니다.

- **RPO(복구 시점 목표):** "데이터를 얼마까지 잃어도 되나?" → **백업 주기**를 정합니다. RPO 1시간이면 시간당 복제.
- **RTO(복구 시간 목표):** "얼마 안에 서비스가 돌아와야 하나?" → **복구 방식**을 정합니다. RTO 1시간이면 타 리전에 미리 이미지·설정이 준비돼 있어야 하고, RTO 하루면 백업에서 조립할 시간이 있죠.

이 둘을 **비즈니스 쪽과 합의**하지 않으면 인프라가 혼자 과잉 설계하거나(비용 폭발) 과소 설계합니다(장애 때 발각). 관리형 DB 이관 글에서 말한 "롤백 조건을 사전 합의"와 같은 성격의 일이에요.

## 복구 리허설이 없으면 백업이 아니다

이 글에서 하나만 가져간다면 이겁니다 — **복제해둔 것으로 실제로 복구해본 적이 없으면, 그건 백업이 아니라 백업처럼 보이는 비용입니다.**

리허설 체크리스트:
```
□ 타 리전에서 스냅샷/이미지로 인스턴스를 실제로 부팅해봤나
□ DB를 복구하고 앱을 붙여 쿼리가 나가는 것까지 확인했나 (엔드포인트 변경 절차 포함)
□ 소요 시간을 측정했나 → 그게 실제 RTO (희망 RTO와 비교)
□ 절차가 문서로 있나 — 새벽 3시의 다른 사람이 따라할 수 있게
□ 분기 1회 일정이 캘린더에 있나
```

## 한 줄 정리

백업의 품질 = **원본과의 독립성**입니다. 다른 리전(지리)·다른 계정(권한)·불변 보존(시간) 세 겹으로 분리하고, 주기와 방식은 **RPO/RTO 합의**로 정하고 — 그리고 **분기마다 실제로 복구해보세요.** 복구해본 적 없는 백업은 슈뢰딩거의 백업입니다.
