> **한 줄 요약:** private 서브넷의 서버가 같은 클라우드의 스토리지를 부를 때, 기본 경로는 **NAT을 거쳐 인터넷으로 나갔다 오는 것**입니다 — 처리 요금이 GB당 붙죠. 엔드포인트는 **VPC 안에서 그 서비스로 직행하는 통로**를 만들어 요금과 노출을 함께 없앱니다.

## 문제 확인부터 — 정말 NAT을 지나고 있나

NAT 글에서 예고한 그 점검입니다. 먼저 우리 NAT 트래픽의 정체를 봅니다.

```bash
# NAT 지표에서 처리량이 큰 시간대를 찾고, 그 시각 서버 쪽에서:
sudo tcpdump -ni any 'dst port 443' -c 200 | awk '{print $5}' | cut -d. -f1-4 | sort | uniq -c | sort -rn | head
# 상위 목적지가 스토리지 서비스 대역이면 → 엔드포인트 전환 후보 확정
```

전형적 범인은 셋입니다 — **① 백업 스크립트가 매일 수십~수백 GB를 버킷으로 업로드, ② 컨테이너 노드가 이미지를 pull(멀티스테이지 다이어트가 여기서도 돈을 아낍니다), ③ 로그 수집기가 중앙 저장소로 전송**(그 글의 파이프라인).

## 두 종류의 통로

**게이트웨이형 (스토리지용, 대개 추가 요금 없음)**
라우팅 테이블에 "이 서비스로 가는 건 이 통로로"를 추가하는 방식. 요금이 안 붙는 경우가 많아 **트래픽이 크면 무조건 1순위**입니다.

```
# private 서브넷의 라우팅 테이블 (before)
10.0.0.0/16      → local
0.0.0.0/0        → nat-gateway        ← 스토리지행도 여기로 나감

# (after) 엔드포인트 경로 추가
10.0.0.0/16      → local
pl-storage(prefix) → vpce-xxxx        ← 스토리지행만 전용 통로로
0.0.0.0/0        → nat-gateway        ← 나머지 인터넷은 그대로
```

핵심은 **더 구체적인 경로가 이깁니다**(longest prefix match) — 0.0.0.0/0보다 특정 서비스 대역이 우선하니, 기존 경로를 지우지 않고 추가만 하면 됩니다. 서브넷 글의 "경로가 정체를 정한다"가 여기서 비용으로 나타나는 셈이죠.

**인터페이스형 (그 외 API 서비스, 시간당 요금)**
VPC 안에 그 서비스의 사설 IP 창구(ENI)를 만들고, DNS가 그 IP로 해석되게 하는 방식. 시간당 요금이 있으니 **NAT 처리 요금과 견줘** 판단합니다 — 트래픽이 작으면 NAT이 더 싸요.

NCP도 같은 그림입니다. Object Storage 등으로 향하는 내부 경로/프라이빗 엔드포인트 제공 여부를 확인하고 라우팅을 분리하는 접근은 동일합니다(이름 지도 글의 원칙대로 세부 스펙만 문서 재확인).

## 전환 절차와 검증

```bash
# 1) 전환 전 기준선 기록
#    NAT 처리량(GB/일), 백업 작업 소요 시간

# 2) 엔드포인트 생성 후, 라우팅이 실제로 바뀌었나 — 경로부터
ip route get 스토리지IP        # 나가는 인터페이스 확인 (변화 없으면 라우팅 반영 안 됨)

# 3) 진짜 검증: NAT을 안 지나는지
#    NAT 지표에서 해당 시간대 처리량이 떨어졌는지 확인 (이게 결정적 증거)
#    + 서버에서 접근이 여전히 되는지
aws s3 ls s3://my-bucket --region ap-northeast-2      # 또는 해당 SDK 호출

# 4) 며칠 뒤 청구서에서 NAT 처리 요금 감소 확인
```

2번과 3번을 나눈 이유가 있습니다 — **"접근이 되네"는 검증이 아닙니다.** 엔드포인트가 잘못 설정돼도 NAT 경로가 살아 있으면 접근은 계속 되니까요(그리고 요금도 계속 나갑니다). **NAT 처리량 하락**만이 진짜 증거예요.

## 부수 효과: 보안이 같이 좋아진다

비용 얘기로 시작했지만, 실은 보안 개선이 더 큰 소득일 수 있습니다.

- 스토리지 접근이 **인터넷을 아예 안 지납니다** — 트래픽 노출 구간이 사라짐
- 엔드포인트 정책으로 "이 VPC에서만 이 버킷 접근 허용" 같은 제약을 걸 수 있어, **키가 유출돼도 외부에서는 못 쓰는** 구조가 됩니다(최소권한 글의 그 폭발 반경 축소를 네트워크로 구현)
- 나아가 "우리 버킷은 VPC 엔드포인트 경유만 허용"으로 잠그면, 공개 버킷 실수 사고의 표면이 줄어듭니다

CSAP/ISMS-P 같은 심사에서 "내부 통신 구간 분리"를 설명해야 할 때도 이 구성이 근거가 되죠.

## 한 줄 정리

private 서브넷의 스토리지 트래픽은 **기본이 NAT 경유(GB당 과금)**입니다. tcpdump로 목적지를 집계해 후보를 확인하고, **게이트웨이형 엔드포인트 + 라우팅 한 줄**로 우회하고, 검증은 "접근되네"가 아니라 **NAT 처리량 하락**으로 — 비용과 노출이 함께 줄어듭니다.
