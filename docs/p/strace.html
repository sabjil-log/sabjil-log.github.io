❯ 프로세스가 뭘 하다 멈췄는지 훔쳐보기 — strace 입문

한 줄 요약: 프로세스가 하는 모든 실질적인 일(파일 열기, 네트워크, 대기)은 결국 커널에 요청(시스템콜)하는 것입니다. strace는 그 대화를 도청하는 도구 — 로그가 침묵할 때 "지금 어떤 요청에서 멈춰 있는지"를 소스 코드 없이도 보여줍니다.

언제 꺼내는 칼인가

  • 프로세스가 멈췄는데(행) 로그는 마지막 줄에서 끊김 — 뭘 기다리는 걸까?
  • 소스가 없는 바이너리가 "설정 파일을 못 찾는다"는데 — 어디를 뒤지고 있는 걸까?
  • 뭔가 느린데 CPU는 놀고 있음 — 시간이 어디로 새는 걸까?

공통점: 앱의 입(로그)은 닫혀 있고, 답은 앱의 행동에 있습니다. tcpdump가 네트워크의 CCTV였다면, strace는 프로세스와 커널 사이의 CCTV예요.

첫 사용: 멈춘 프로세스에 붙기

sudo strace -p 12345          # 떠 있는 프로세스에 부착

멈춘 프로세스에 붙으면 보통 마지막 줄 하나가 미완성인 채 걸려 있습니다. 그 한 줄이 진단서예요.

read(7, ...                    ← fd 7에서 읽기를 기다리는 중
futex(0x7f..., FUTEX_WAIT ...  ← 락/다른 스레드를 기다리는 중
connect(3, {..., port 5432} ...← DB 접속 자체가 안 끝남
wait4(-1, ...                  ← 자식 프로세스를 기다리는 중

read(7...)에서 멈췄다면 — fd 7이 뭔지 이어서 확인합니다.

ls -l /proc/12345/fd/7
# → socket:[398211]  이면 네트워크 대기 (ss로 어느 연결인지 추적)
# → /var/log/x.log   이면 파일 대기 (NFS 행이 단골)

fd 글에서 본 그 /proc 디렉토리가 여기서 다시 활약하죠. "멈춤 = 어떤 syscall + 어떤 fd"로 번역되는 순간, 막연한 행이 구체적인 용의자(DB, NFS, 락)로 바뀝니다.

두 번째 사용: 파일을 어디서 찾는지

"설정을 못 읽어요"류 문제의 정답 기계입니다.

strace -f -e trace=openat,stat,access ./myapp 2>&1 | grep -v ENOENT | head -30
# 또는 반대로 — 어디서 못 찾고 있는지
strace -e trace=openat ./myapp 2>&1 | grep ENOENT | head

openat(AT_FDCWD, "/etc/myapp/config.yml", O_RDONLY) = -1 ENOENT (No such file...)
openat(AT_FDCWD, "./config.yml", O_RDONLY) = 3      ← 결국 여기서 찾았다

앱이 실제로 뒤진 경로들이 순서대로 나옵니다. cron 환경 글의 "작업 디렉토리가 달라서" 문제, docker 볼륨 글의 "마운트 경로가 어긋나서" 문제가 여기서 즉시 자백해요. -f는 자식 프로세스까지 추적 — 래퍼 스크립트가 진짜 바이너리를 띄우는 구조면 필수입니다.

세 번째 사용: 시간이 어디로 새나

strace -c -p 12345      # 잠시 붙였다 Ctrl+C — syscall별 횟수·소요시간 집계표

% time  seconds   calls  syscall
 88.1   4.410000   1203  poll        ← 대부분 대기
  9.2   0.460000  30841  stat        ← stat을 3만 번?!

집계표는 프로파일러의 축소판입니다. stat 3만 번 — 매 요청마다 파일 존재를 확인하는 코드가 범인이라는 식의 발견이 여기서 나옵니다. 개별 호출의 지연을 보려면 -T(각 콜 소요시간), 타임스탬프는 -tt.

주의사항 — 도청은 공짜가 아니다

strace는 대상 프로세스를 매 syscall마다 멈췄다 재개시킵니다. syscall이 잦은 프로세스는 수 배 느려질 수 있어요. 그래서 운영 서버에서는 —

  • 짧게 붙였다 뗍니다 (-c로 몇 초 집계, 또는 timeout 10 strace ...)
  • 출력은 파일로: -o /tmp/trace.txt (터미널 출력 자체가 병목이 되기도)
  • 이미 죽어가는 프로세스 분석이면 부담 없이, 멀쩡히 일하는 프로세스면 피크 시간을 피해서

더 가벼운 대안이 필요한 상황(상시 관찰, 고빈도)이면 perf나 eBPF 계열(bpftrace)이 다음 단계인데, "가끔 꺼내는 진단 칼"로는 strace가 배우기도 쉽고 어디에나 있습니다.

한 줄 정리

strace의 용법은 사실상 세 개입니다 — 멈춤엔 -p로 붙어 마지막 줄 읽기(+ /proc/PID/fd로 fd 정체 확인), 파일 문제엔 -e trace=openat, 성능엔 -c 집계. 로그가 침묵할 때, 행동은 거짓말을 못 합니다.
