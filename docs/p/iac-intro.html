❯ 콘솔 클릭을 코드로 옮기면 뭐가 달라지나 — IaC 입문

한 줄 요약: IaC는 인프라를 텍스트 파일로 선언하고 도구가 그 상태로 맞춰주는 것입니다. 얻는 건 셋 — 재현(같은 환경을 다시), 기록(누가 언제 왜 바꿨는지 git에), 검토(적용 전 diff). 첫 도입의 진짜 장벽은 문법이 아니라 상태 파일과 이미 있는 자원입니다.

콘솔 운영의 한계

300개 계정을 만지는 MSP라면 익숙한 장면 — "이 고객사 VPC, 그때 누가 어떻게 만들었죠?" 답은 콘솔 어딘가의 감사 로그와 기억 속에만 있습니다. 스테이징을 운영과 똑같이 만들려면 클릭을 수십 번 다시 해야 하고, 사소한 차이(ACG 규칙 하나)가 "스테이징에선 되는데"의 원인이 되죠.

IaC는 이 셋을 구조로 풉니다.

# main.tf — "이런 상태이길 원한다"는 선언
resource "ncloud_vpc" "main" {
  name            = "goil-prod"
  ipv4_cidr_block = "10.10.0.0/16"
}
resource "ncloud_subnet" "web" {
  vpc_no      = ncloud_vpc.main.id
  subnet      = "10.10.1.0/24"
  zone        = "KR-2"
  subnet_type = "PUBLIC"
  name        = "goil-prod-web"
}

핵심 동작은 plan → apply 두 단계입니다. plan이 "현재 상태와 선언의 차이"를 diff로 보여주고, apply가 그 차이만 적용합니다. 적용 전에 뭐가 바뀔지 본다 — 이게 콘솔과의 결정적 차이예요. 리뷰가 가능해지니 PR로 인프라 변경을 승인하는 문화가 따라옵니다.

첫 도입의 진짜 장벽 셋

① 상태 파일(state). 도구는 "내가 만든 자원이 뭔지"를 상태 파일에 기억합니다. 이 파일이 진실의 원장이에요 — 잃으면 도구가 자원을 못 알아보고, 둘이 동시에 쓰면 꼬입니다. 그래서 첫날부터 원격 백엔드(오브젝트 스토리지 + 잠금)에 두는 게 규칙입니다. 로컬 노트북의 state 파일은 스냅샷 글의 "같은 도시에 둔 백업"과 같은 취약점이죠.

② 이미 있는 자원. 신규 프로젝트면 편한데, 대부분은 콘솔로 만든 자원이 이미 있습니다. 선택지는 import(기존 자원을 상태에 편입 — 코드도 맞춰 써야 함) 또는 신규부터만 IaC(기존은 그대로, 새 것만 코드로). 실무 정석은 후자로 시작해 중요 자원부터 점진 import. 한 번에 다 옮기려다 멈추는 팀이 많습니다 — 태그 정책 글의 "신규부터 강제"와 같은 감각이에요.

③ 드리프트(drift). 누군가 콘솔에서 손으로 바꾸면 코드와 현실이 어긋납니다. plan이 그 차이를 잡아내지만(이게 IaC의 감시 기능), 되돌릴지 코드에 반영할지 결정이 필요하죠. 조직 규칙이 없으면 "코드는 장식, 현실은 콘솔"로 퇴행합니다. 처방은 정기 plan(드리프트 감지 알람)과 "콘솔 변경 금지 자원" 목록.

폭발 반경을 설계하라

한 상태 파일에 전부 넣으면 apply 한 번의 실수가 전부를 건드립니다. 리전·AZ 글의 장애 반경이 IaC에서는 상태 파일 경계로 나타나요.

환경별(prod / stg) × 계층별(network / compute / data)로 상태를 분리
→ data 계층은 별도 상태 + 삭제 방지(prevent_destroy)
→ apply 권한도 환경별로 (IAM 글의 최소권한)

특히 DB·스토리지는 prevent_destroy — "이름 하나 바꾸려다 재생성(=삭제 후 생성)"이 IaC 사고의 고전이라서요. plan에서 -/+(destroy and create)가 보이면 반드시 멈춰 읽는 습관이 안전판입니다.

그래서 얻는 것 — MSP 관점

  • 고객사별 표준 아키텍처를 모듈로 — VPC+서브넷+NAT+배스천 세트를 변수 몇 개로 찍어냄. 300개 계정의 일관성이 여기서 나옵니다.
  • 컴플라이언스 근거 — CSAP/ISMS-P 심사에서 "이 구성이 정책대로다"를 코드로 보여줄 수 있음
  • 재해 복구 — 크로스 리전 글의 RTO를 줄이는 결정적 도구. 타 리전에 같은 코드를 apply하면 골격이 재현됩니다.

시작 절차

1. 원격 상태 백엔드 먼저 (잠금 포함)
2. 신규 자원 하나(예: 서브넷 하나)를 코드로 — plan/apply 감각 익히기
3. 환경·계층 분리 구조 잡기, 데이터 계층엔 prevent_destroy
4. PR 리뷰에 plan 결과 첨부하는 규칙
5. 기존 자원은 중요도 순으로 import

한 줄 정리

IaC의 가치는 plan(적용 전 diff)·git(기록)·재현이고, 첫 장벽은 원격 상태·기존 자원·드리프트입니다. 상태를 환경×계층으로 나눠 폭발 반경을 좁히고, 데이터엔 삭제 방지, -/+가 보이면 멈추기 — 신규부터 시작해 점진 편입이 살아남는 도입법입니다.
