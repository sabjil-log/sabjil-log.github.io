❯ 같은 문서를 두 번 임베딩하지 않기 — RAG 인덱싱 비용 줄이기

한 줄 요약: 임베딩은 같은 입력에 항상 같은 출력입니다 — 즉 캐시가 완벽하게 통하는 연산이죠. 청크 내용의 해시를 키로 저장해두면, 문서를 다시 인덱싱할 때 바뀐 청크만 계산합니다. rsync가 파일에 한 일을 임베딩에 하는 것.

흔한 낭비의 구조

사내 문서 5,000개로 RAG를 만들었습니다. 매일 밤 인덱싱 배치가 돕니다.

for doc in all_docs():             # 5,000개
    for chunk in split(doc):       # 평균 20청크 = 10만 청크
        vec = embed(chunk)         # 매일 10만 번 임베딩
        upsert(chunk, vec)

그런데 하루에 실제로 바뀌는 문서는 5~10개입니다. 10만 번 중 99.9%가 어제와 완전히 같은 텍스트를 또 계산하는 거죠. API형이면 그대로 요금이고, 자체 서빙이면 GPU 시간입니다.

처방: 내용 해시를 키로

임베딩은 결정적(deterministic) 함수라, 입력이 같으면 결과를 재사용해도 100% 동일합니다. 그래서 캐시 키는 내용 그 자체 —

import hashlib

def chunk_key(text, model_id):
    # 모델을 바꾸면 벡터가 호환되지 않으므로 키에 모델을 포함
    h = hashlib.sha256(text.encode()).hexdigest()[:32]
    return f"{model_id}:{h}"

def embed_cached(text, model_id, cache):
    k = chunk_key(text, model_id)
    hit = cache.get(k)
    if hit:
        return hit                      # 계산 생략
    vec = embed(text, model_id)
    cache.set(k, vec)
    return vec

model_id를 키에 넣는 게 중요합니다 — 임베딩 글에서 말한 그 제약(모델 교체 = 재인덱싱)이 캐시 오염으로 나타나지 않게 하는 안전장치예요.

문서 단위 스킵까지 — 두 단계 게이트

청크 해시만으로도 계산은 아끼지만, 문서를 쪼개고 해시를 뜨는 일 자체도 비용입니다. 앞에 게이트를 하나 더 둡니다.

① 문서 게이트: 원본 파일의 해시(또는 수정시각+크기)가 지난번과 같으면 → 그 문서 통째로 스킵
② 청크 게이트: 바뀐 문서만 쪼개고, 청크 해시로 개별 판정 → 바뀐 청크만 임베딩

①이 rsync의 파일 목록 비교, ②가 델타 전송에 해당합니다. 실무 효과는 극적이에요 — 매일 10만 청크가 수십~수백 청크로.

놓치기 쉬운 것들

① 삭제 처리. 캐시는 "새로 계산할 것"만 줄입니다. 문서에서 사라진 청크를 벡터DB에서 지우지 않으면 유령 문서가 검색됩니다 — 없어진 규정이 답변 근거로 인용되는 사고. 문서별로 현재 청크 키 집합을 기록해두고, 인덱싱 후 차집합을 삭제하세요. (rsync의 --delete와 같은 역할이고, 같은 이유로 조심스럽게.)

② 청킹 규칙을 바꾸면 전부 무효. 청크 경계가 달라지면 텍스트가 달라지니 해시도 전부 새것 — 청킹 파라미터 변경은 사실상 전체 재인덱싱입니다. 그래서 청킹 규칙도 키에 포함시키는 구현이 안전해요(model:chunkver:hash).

③ 중복 문서의 자동 이득. 사내 문서는 같은 문단이 여러 파일에 복붙돼 있는 경우가 흔합니다. 내용 해시 캐시는 이걸 자동으로 중복 제거해줍니다 — 계산도 아끼고, 검색 결과에 같은 내용이 여러 번 뜨는 문제도 줄어요(리랭커 앞단의 후보 다양성 확보).

④ 저장은 가볍게. 캐시 값은 벡터(수 KB)입니다. 10만 청크 × 1024차원이면 수백 MB — 로컬 SQLite나 Redis, 또는 벡터DB 자체를 캐시로 겸용(이미 있는 벡터를 읽어 재사용)해도 됩니다. 별도 저장소를 만들기 전에 벡터DB에 해시를 메타데이터로 넣고 조회하는 방식이 가장 단순한 구현입니다.

인덱싱 파이프라인 체크리스트

□ 문서 해시로 무변경 문서 스킵
□ 청크 해시(+모델·청킹 버전)로 개별 스킵
□ 사라진 청크는 차집합 삭제
□ 인덱싱 로그에 (신규/재사용/삭제) 카운트 출력 ← 캐시가 실제로 듣는지 확인
□ 실패 시 재개 가능 (중단된 배치가 처음부터 돌지 않게)

마지막 두 개가 운영의 눈입니다. "재사용 99,900 / 신규 120"이 매일 로그에 찍히면 파이프라인이 건강한 것이고, 그 비율이 어느 날 깨지면 무언가(모델·청킹 버전) 바뀐 겁니다.

한 줄 정리

임베딩은 결정적이니 내용 해시로 캐시하면 공짜 절감입니다. 문서 게이트 + 청크 게이트로 매일 전체 재계산을 델타로 바꾸고, 모델·청킹 버전을 키에 포함하고, 사라진 청크 삭제를 잊지 마세요 — 인덱싱 비용은 대개 여기서 90% 이상 빠집니다.
