❯ LLM 응답 파싱 지옥에서 탈출하기 — 구조화 출력 제대로 쓰는 법

한 줄 요약: 코드가 LLM 응답을 이어받으려면 형식이 매번, 반드시 같아야 합니다. 방법은 강제력 순으로 4단계 — 프롬프트 부탁 < JSON 모드 < 도구 호출(tool use) < 스키마 강제. 파싱 코드로 방어하지 말고, 가능한 가장 높은 단계로 올라가는 게 답입니다.

지옥의 풍경

LLM으로 정보 추출을 붙이면 이런 코드가 자라기 시작합니다.

text = resp.strip()
if text.startswith("```json"): text = text[7:]      # 마크다운 펜스 제거
if text.startswith("```"):     text = text[3:]
text = text.rsplit("```", 1)[0]
text = text[text.find("{"):]                         # "네, 알겠습니다!" 서두 제거
data = json.loads(text)                              # 그래도 가끔 터짐

동작은 합니다 — 99%는. 문제는 하루 1만 건이면 1%가 100건이라는 것. "JSON으로만 답해 주세요"는 부탁이지 계약이 아니거든요. 모델은 어느 날 친절하게 설명을 덧붙이고, 필드명을 창의적으로 바꾸고, 숫자를 문자열로 감쌉니다.

강제력의 사다리 — 4단계

1단 · 프롬프트 부탁 — "JSON으로만, 코드펜스 없이". 프로토타입용. 강제력 없음.

2단 · JSON 모드 — 벤더가 제공하는 "출력은 유효한 JSON" 스위치. 문법은 보장되지만 구조는 아닙니다 — 유효한 JSON이면서 내가 원한 필드가 없는 답이 얼마든지 가능해요.

3단 · 도구 호출(tool use) 전용 — 에이전트 글의 그 메커니즘을 추출에 역이용하는 것. "이 도구를 호출해"라고 하면 모델은 도구의 인자 스키마에 맞는 구조를 만들어야 합니다. 잡담·서두·펜스가 끼어들 자리가 아예 없죠.

tools = [{
  "name": "save_extraction",
  "description": "문서에서 추출한 정보를 저장한다",
  "input_schema": {
    "type": "object",
    "properties": {
      "company":  {"type": "string"},
      "amount":   {"type": "integer", "description": "원 단위, 숫자만"},
      "due_date": {"type": "string", "description": "YYYY-MM-DD"},
      "confident":{"type": "boolean", "description": "추출 확신 여부"}
    },
    "required": ["company", "amount", "confident"]
  }
}]
# 응답에서 resp.tool_calls[0].args 를 꺼내면 이미 dict — 파싱 코드 자체가 사라짐

4단 · 스키마 강제(constrained decoding) — 벤더/서빙에 따라 "이 JSON 스키마에 맞는 토큰만 생성하게" 디코딩 단계에서 묶는 기능(structured outputs, vLLM의 guided decoding 등). 문법+구조가 생성 과정에서 보장되는 가장 강한 단계입니다. 쓸 수 있으면 이걸 쓰고, 없으면 3단이 실전 표준이에요.

스키마가 곧 프롬프트다

3~4단에서 품질을 가르는 건 스키마의 설명(description)입니다 — 도구 명세가 절반이라던 그 원칙 그대로.

  • amount: integer 만 쓰지 말고 "원 단위, 쉼표 없이 숫자만" — 단위·형식 모호성이 오답의 주범.
  • enum을 적극적으로 — "category": {"enum": ["환불","배송","기타"]} 면 창의적 카테고리 발명이 원천 봉쇄됩니다.
  • "모름"의 자리를 만들 것 — 환각 글의 그 출구가 여기서도 필요합니다. confident: boolean 이나 nullable 필드가 없으면, 모델은 required를 채우려고 없는 값을 지어냅니다. 스키마 강제의 역설 — 형식을 조일수록 내용 환각이 늘 수 있어요. 출구 필드가 해독제입니다.

그래도 남는 함정들

  • 구조 보장 ≠ 내용 보장. due_date가 완벽한 YYYY-MM-DD인데 문서에 없는 날짜일 수 있습니다. 형식 검증(pydantic 등)과 별개로 값 검증(원문 대조, 범위 체크)은 남습니다.
  • 너무 큰 스키마. 필드 30개짜리 한 방 추출은 품질이 급락합니다. 문서 하나에 여러 주제면 나눠 뽑으세요 — 청킹의 "한 조각 = 한 생각"이 스키마에도 적용됩니다.
  • 재시도 설계. 검증 실패 시 에러 내용을 붙여 1회 재요청("due_date가 스키마와 다릅니다: ...")하는 루프가 실전 표준. 단, 재시도는 1~2회로 — 무한 루프는 에이전트 글의 그 상한 원칙.
  • usage 감시. 스키마가 커지면 그만큼 입력 토큰입니다. 고정 스키마는 프롬프트 캐싱 글의 규칙대로 앞쪽에 고정 배치 — 도구 명세는 원래 앞에 가니 자연스럽게 캐시를 탑니다.

한 줄 정리

파싱 방어 코드가 자라고 있다면 그건 신호입니다 — 사다리를 올라갈 때라는. 부탁(1) 말고 도구 호출(3)이나 스키마 강제(4)로, 스키마에는 설명·enum·'모름'의 출구를 담고, 형식 검증 뒤 값 검증까지. 파싱 지옥의 출구는 정규식이 아니라 계약입니다.
