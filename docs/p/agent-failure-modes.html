❯ 에이전트 실패 모드 도감 — 루프·환각 실행·권한 초과·조용한 포기

한 줄 요약: 챗봇의 실패는 틀린 답이지만 에이전트의 실패는 틀린 행동입니다. 운영에서 반복되는 유형은 여섯 — 무한 루프, 환각 실행, 권한 초과, 조용한 포기, 컨텍스트 붕괴, 부분 완료. 각각 감지 지표와 차단 장치가 다르니, 도감처럼 알아두면 사고가 났을 때 "어느 종인지"부터 가려집니다.

① 무한 루프 — 같은 도구를 계속 부른다

증상: 검색 → 결과 불만족 → 같은 검색 → … 토큰과 비용이 곱으로 뜁니다. 에이전트 글에서 말한 그 "루프 상한"이 없을 때의 기본 실패.

원인: 도구 결과가 모델이 기대한 형식이 아니거나(빈 결과, 에러 문자열), 종료 조건이 프롬프트에 없거나, 도구 설명이 "언제 그만둘지"를 안 말해줘서.

장치: 호출 횟수 상한(작업당), 같은 도구+같은 인자 반복 감지(2회면 개입), 예산(토큰·시간) 상한. 감지 지표는 작업당 평균 도구 호출 수 — 이게 튀면 루프가 늘고 있는 겁니다.

② 환각 실행 — 없는 도구·없는 인자를 부른다

증상: 존재하지 않는 함수명, 스키마에 없는 파라미터, 지어낸 ID(order_id: "ORD-12345" — 실제 조회 없이 만든 값)로 실행 요청. 환각 글의 그 관성이 행동으로 나타나는 것.

장치: 구조화 출력 글의 스키마 강제(도구 호출 단계에서 인자 검증 — 검증 실패는 실행 없이 모델에 에러로 되돌리기), 그리고 ID류는 반드시 이전 도구 결과에서 왔는지 추적(조회 안 한 ID로 삭제·결제 요청이 오면 차단). 감지 지표는 인자 검증 실패율.

③ 권한 초과 — 할 수 있어서 했다

증상: 조회만 시켰는데 "정리하는 게 좋겠다"며 삭제. 프롬프트 주입 글의 그 시나리오가 주입 없이도 모델의 과잉 친절로 발생합니다.

장치: 도구 권한을 작업 단위로 최소화(읽기 작업엔 쓰기 도구 자체를 안 줌 — 멀티에이전트 글의 조회/실행 분리), 파괴적 작업엔 사람 승인 게이트, 그리고 드라이런 모드(실행 대신 "하려는 것"을 보고). 감지 지표는 승인 게이트 도달 건수 대비 승인 거부율 — 거부가 많으면 모델이 과하게 행동하려는 신호.

④ 조용한 포기 — 못 했는데 했다고 한다

증상: 도구가 에러를 반환했는데 모델이 "완료했습니다"라고 보고. 또는 3단계 중 2단계에서 막혔는데 결과를 그럴듯하게 요약. 가장 위험한 유형 — 로그를 안 보면 모릅니다.

원인: 에러 메시지가 모델에게 "실패"로 안 읽히거나(HTTP 200에 담긴 에러 JSON), 프롬프트가 "항상 결과를 보고하라"고 압박해서.

장치: 도구 결과에 성공/실패를 명시적 필드로(모델이 해석할 필요 없게), 최종 보고에 "수행한 도구 호출 목록과 각 결과"를 구조화로 첨부하게 강제 — 그러면 "완료"라는 말과 실제 실행 기록을 코드가 대조할 수 있습니다. 감지 지표는 보고 내용 vs 도구 성공 기록의 불일치 건수.

⑤ 컨텍스트 붕괴 — 길어지다 처음을 잊는다

증상: 긴 작업 후반에 초반의 제약("prod는 건드리지 마")을 잊고 위반. 컨텍스트 윈도우 글의 "가운데 흐림"과 밀려남이 행동 제약 상실로 나타나는 것.

장치: 핵심 제약은 시스템 프롬프트에(시스템/유저 글의 위계), 긴 작업은 에이전트 메모리 글의 작업 노트 패턴으로 제약·진행 상태를 매 스텝 다시 읽게, 그리고 제약은 프롬프트에만 두지 말고 도구 레벨에서도 강제(prod 리소스는 도구가 거부). 감지 지표는 작업 길이(스텝 수)별 제약 위반율.

⑥ 부분 완료 — 중간에 멈춘 채 끝

증상: 5개 파일 중 3개만 수정하고 종료, 또는 예산 상한(①의 장치!)에 걸려 중간 상태로 정지. 안전장치가 만드는 2차 실패이기도 합니다.

장치: 작업을 멱등하게 설계(다시 돌려도 안전 — 배치 API 글의 그 원칙), 중단 시 어디까지 했는지 구조화 보고를 필수로, 재개 가능한 체크포인트(스팟 글의 그 감각). 감지 지표는 정상 종료 vs 상한 종료 비율.

운영 대시보드 여섯 줄

작업당 평균 도구 호출 수         ← ① 루프
인자 검증 실패율                 ← ② 환각 실행
승인 게이트 거부율               ← ③ 권한 초과
보고-실행 기록 불일치 건수        ← ④ 조용한 포기
스텝 수별 제약 위반율            ← ⑤ 컨텍스트 붕괴
상한 종료 비율                  ← ⑥ 부분 완료

LLM 평가 글의 골든셋에 "실패해야 정상인 과제"(권한 없는 요청, 존재하지 않는 대상)를 섞어두면, 이 여섯 지표가 배포 전에 측정됩니다. 그리고 감사 로그 글의 원칙 — 모든 도구 호출은 누가(어느 에이전트·어느 사용자 세션)·언제·무엇을·결과로 기록. 사고가 났을 때 "어느 종인지" 가리는 건 결국 이 로그입니다.

한 줄 정리

에이전트 실패는 여섯 종 — 루프·환각 실행·권한 초과·조용한 포기·컨텍스트 붕괴·부분 완료. 각각 다른 감지 지표와 차단 장치가 있고, 공통 기반은 구조화된 도구 결과 + 실행 기록 로그 + 골든셋의 '실패해야 정상' 과제입니다. 가장 무서운 건 ④ — 못 했는데 했다고 하는 것이니, 말이 아니라 기록을 믿는 구조를 만드세요.
