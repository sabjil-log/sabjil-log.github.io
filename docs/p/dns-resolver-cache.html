❯ DNS는 맞는데 가끔만 느리다 — 리졸버 캐시 4층과 hosts 우선순위

한 줄 요약: 이름 하나를 푸는 데도 hosts 파일 → 로컬 캐시(systemd-resolved 등) → 리졸버 캐시 → 권위 서버의 4층을 거칩니다. "가끔만 느림"은 대개 캐시 미스의 순간(TTL 만료 직후, 첫 조회)이고, "고쳤는데 계속 안 됨"은 대개 어느 층의 낡은 캐시(특히 실패를 기억하는 negative 캐시)입니다.

증상 두 가지, 원인은 한 구조

증상 A: API 호출이 대부분 20ms인데 가끔 1초 넘게 튐 — 애플리케이션은 무죄, p95 그래프만 지저분함. 증상 B: DNS 레코드를 고쳤는데(그 글의 TTL도 확인했는데) 특정 서버에서만 계속 옛 주소로 감.

둘 다 같은 구조에서 나옵니다 — DNS 조회는 한 번의 질문이 아니라 캐시 계단을 내려가는 과정이라는 것.

4층 구조 — 질문이 여행하는 길

① /etc/hosts          — 캐시 아님, '정답 강제' (조회 전에 먼저 봄)
② 로컬 스텁 캐시       — systemd-resolved (127.0.0.53), nscd 등
③ 리졸버 캐시          — /etc/resolv.conf의 그 서버 (사내 DNS, 8.8.8.8, VPC 리졸버)
④ 권위 서버            — 진짜 원본 (dns-records 글의 그 안내판)

각 층은 답을 TTL만큼 기억합니다. 평소엔 ①~②에서 끝나 0ms대 — 그러다 TTL이 만료된 직후의 첫 조회만 ④까지 내려갔다 오느라 느린 거죠. 증상 A의 정체입니다. 특히 TTL을 아주 짧게(수십 초) 잡은 레코드나, 조회가 뜸해 캐시가 자주 식는 배치성 워크로드에서 도드라져요.

한 층씩 캐시를 우회하며 어디가 느린지 재는 법:

time getent hosts api.example.com     # ①~② 포함한 실제 앱 경로의 시간
resolvectl query api.example.com      # ② systemd-resolved 기준 (캐시 여부 표시)
dig api.example.com                   # ②를 건너뛰고 ③에 직접 — resolv.conf의 서버로
dig @8.8.8.8 api.example.com          # ③도 바꿔서 — 사내 리졸버가 범인인지 판별
dig @권위서버 api.example.com +norecurse   # ④ 원본 직행

dig는 빠른데 앱은 느리다? — dig는 ②를 안 거치므로, 로컬 스텁이나 앱 자체의 리졸버 설정(컨테이너의 DNS 설정, JVM의 자체 캐시처럼 앱 레벨 캐시가 또 있는 경우도!) 쪽으로 용의선이 좁혀집니다.

함정 1 — 실패도 기억된다 (negative 캐시)

"서버 띄우기 전에 접속해봤다가 안 됐고, 서버 띄운 뒤에도 한동안 안 됨" — NXDOMAIN(그런 이름 없음)이라는 실패 응답도 캐시되기 때문입니다. 새 레코드를 만들자마자 조회하면, 방금의 "없음"이 각 층에 기억돼 있어서 생긴 지 한참 뒤까지 없다고 답해요. 새 서브도메인 배포 직후의 단골 미스터리 — 기다리거나, 아래 flush로 층을 비웁니다.

sudo resolvectl flush-caches          # ② systemd-resolved 비우기
resolvectl statistics                 # 캐시 히트/미스 통계 — 진단에도 유용

③(사내/벤더 리졸버)의 캐시는 우리가 못 비우는 경우가 많으니, negative TTL이 지나기를 기다리는 것까지 계획에 넣는 게 현실적입니다. 애초에 배포 절차를 "레코드 먼저, 조회는 나중"으로 잡는 게 백신이고요.

함정 2 — hosts 파일은 캐시보다 세다

①은 캐시가 아니라 오버라이드입니다. 조회 자체를 안 하고 그 값을 씁니다 — TTL도 만료도 없어요. 그래서 강력한 도구이자 시한폭탄입니다.

  • 도구로: 이관 리허설 때 10.0.9.99 api.example.com 한 줄이면 DNS 전환 없이 새 서버를 테스트할 수 있죠 (curl 글의 --resolve와 같은 용도 — 그쪽이 더 안전하긴 합니다. 명령 하나에만 적용되니까).
  • 폭탄으로: 그 한 줄을 지우는 걸 잊으면, 전 세계 DNS가 다 바뀌어도 그 서버만 영원히 옛 주소로 갑니다. 증상 B의 단골 범인 — "고쳤는데 이 서버만 안 돼요"는 cat /etc/hosts부터 보세요. 30초짜리 확인이 반나절 수사를 아낍니다.

우선순위 자체도 설정입니다 — /etc/nsswitch.conf의 hosts: files dns 줄이 "① 먼저, 그다음 DNS"라는 규칙의 출처예요. 순서가 다르게 고쳐진 서버(드물지만 있습니다)는 이 상식이 안 통하니, 정말 미궁이면 여기까지 확인.

운영 감각 — 캐시는 적이 아니다

증상만 보면 캐시를 끄고 싶어지는데, 캐시가 없으면 모든 조회가 ④행이라 지연·리졸버 부하·권위 서버 의존이 전부 나빠집니다(CDN 글의 그 논리 — 캐시는 성능의 뼈대). 실무 정석은 반대 방향이에요.

  • 자주 부르는 외부 API가 있다면 커넥션 재사용(TIME_WAIT 글의 keep-alive)으로 조회 횟수 자체를 줄이고
  • 마이크로서비스 간 호출이 많으면 로컬 캐시 데몬(②)이 제 역할을 하는지 resolvectl statistics로 확인하고
  • TTL은 dns-records 글의 원칙대로 — 평상시 넉넉히, 변경 계획 시에만 미리 낮추기

한 줄 정리

DNS 조회는 hosts → 로컬 캐시 → 리졸버 → 권위의 계단이고, "가끔 느림"은 TTL 만료 순간, "계속 옛 주소"는 낡은 캐시나 잊힌 hosts 한 줄입니다. getent → resolvectl → dig → dig @8.8.8.8로 층을 벗겨가며 재고, 실패도 캐시된다는 것(negative)까지 기억하면 — DNS 미스터리의 9할이 풀립니다.
