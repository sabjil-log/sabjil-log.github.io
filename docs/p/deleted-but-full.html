❯ 파일을 지웠는데 용량이 안 줄었다 — 열린 fd와 lsof +L1

한 줄 요약: rm은 파일의 이름(디렉토리 항목)을 지우는 것이고, 실제 데이터는 그 파일을 열어둔 프로세스가 전부 닫을 때 회수됩니다. 로그 파일을 지웠는데 df가 그대로라면, 누군가 아직 그 파일을 쓰고 있다는 뜻 — lsof +L1이 범인을 지목합니다.

상황

$ du -sh /var/log/app/        # 12M
$ df -h /var                  # 사용률 97%  — 어디 갔지?

du(보이는 파일의 합)와 df(디스크 실제 사용)가 크게 어긋나면 이 현상입니다. 며칠 전 20GB짜리 로그를 rm으로 지웠는데, 그 로그를 쓰던 앱은 여전히 같은 파일 핸들에 계속 쓰고 있습니다. 이름은 사라졌지만 파일은 살아 있고, 심지어 계속 커지고 있어요.

원리: 이름과 실체는 다르다

inode 글에서 본 구조입니다 — 파일의 실체는 inode + 데이터 블록이고, 디렉토리 항목은 그 실체를 가리키는 이름표일 뿐이에요. rm은 이름표를 뗍니다. 실체는 참조 수(이름 개수 + 열어둔 fd 개수)가 0이 될 때 회수됩니다.

rm 전:  이름표 1 + 열린 fd 1  → 참조 2
rm 후:  이름표 0 + 열린 fd 1  → 참조 1  ← 살아 있음, 디스크 점유 중
프로세스 종료/close 후:       → 참조 0  ← 그때 회수

리눅스가 "쓰는 중인 파일을 지울 수 있는" 이유이자, 그 대가입니다.

범인 찾기

sudo lsof +L1
# COMMAND   PID  USER  FD   TYPE  SIZE/OFF    NLINK  NAME
# java    23841   app  7w   REG   21474836480     0  /var/log/app/app.log (deleted)

+L1은 링크 수(NLINK)가 1 미만인 열린 파일 — 즉 이름은 없는데 열려 있는 파일만 보여줍니다. SIZE 컬럼이 곧 회수 가능한 용량이고, PID와 FD 번호가 처방의 재료예요.

회수하는 세 가지 방법

① 프로세스 재시작 — 가장 확실. 앱이 fd를 닫으면 즉시 회수됩니다. 단, 서비스 중단이 따르죠.

② 파일을 비우기(truncate) — 재시작 없이

sudo truncate -s 0 /proc/23841/fd/7
# 또는:  : > /proc/23841/fd/7

/proc/PID/fd/N은 그 프로세스가 열어둔 파일로 가는 살아있는 통로입니다(fd·strace 글에서 본 그 디렉토리). 이름이 지워진 파일도 이 경로로는 접근되니, 내용을 0바이트로 잘라버리면 공간이 즉시 돌아옵니다. 앱은 계속 쓰지만 처음부터 다시 쌓이는 셈 — 운영 중 응급 처치의 정석입니다.

③ 로그라면 로테이션 도구에 맡기기 — 근본 해결. 아래에서.

재발 방지: 로그는 rm 하지 않는다

이 사고의 8할은 로그 파일을 손으로 지워서 납니다. 정석은 둘 중 하나예요.

  • logrotate + copytruncate: 로그를 복사해두고 원본을 잘라냅니다(truncate). 앱은 같은 fd로 계속 쓰니 재시작 불필요. 단, 복사와 잘라내기 사이의 아주 짧은 순간에 쓰인 로그는 유실될 수 있습니다.
  • logrotate + 시그널(재열기): 파일을 옮기고 앱에 "로그 다시 열어"(SIGHUP/USR1)를 보냅니다. 유실 없이 깔끔하지만 앱이 그 시그널을 지원해야 합니다(nginx 등은 지원).
# /etc/logrotate.d/app
/var/log/app/*.log {
    daily
    rotate 14
    compress
    copytruncate        # 앱이 재열기를 지원하면 이 줄 대신 postrotate에서 시그널
    missingok
}

그리고 근본의 근본 — 로그가 로컬 디스크를 채우는 구조 자체가 문제라는 것. 로그 중앙화 글의 그 파이프라인이면 로컬은 며칠치만 두고 중앙으로 보내니, 이 사고가 성립할 여지가 줄어듭니다.

진단 루틴 정리

df -h; du -sh /var/* | sort -h | tail        # ① df ≫ du 인가 (어긋남 확인)
sudo lsof +L1 | sort -k7 -n | tail           # ② 지워졌는데 열린 파일, 큰 것부터
sudo truncate -s 0 /proc/PID/fd/N            # ③ 응급 회수 (로그류에만)
# ④ logrotate 설정 점검 · 중앙화 검토

주의: ③은 로그처럼 내용을 버려도 되는 파일에만 하세요. DB 데이터 파일이나 업로드 파일이 lsof +L1에 잡혔다면, 그건 지우면 안 되는 걸 지운 겁니다 — 프로세스가 살아 있는 지금이 복구 가능한 유일한 시간이에요(cp /proc/PID/fd/N 복구경로).

한 줄 정리

rm은 이름표만 뗍니다. df와 du가 어긋나면 lsof +L1로 "지워졌는데 열린 파일"을 찾고, 로그면 /proc/PID/fd/N을 truncate로 응급 회수, 그리고 앞으로는 rm 대신 logrotate — 로그는 손으로 지우는 게 아니라 정책으로 돌리는 겁니다.
