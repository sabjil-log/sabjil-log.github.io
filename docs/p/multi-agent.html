❯ 에이전트를 여러 개 두면 더 똑똑해질까 — 멀티에이전트, 언제 쪼개나

한 줄 요약: 멀티에이전트는 마법이 아니라 조직 설계입니다. 얻는 것은 분업(컨텍스트·도구 격리)과 병렬성, 잃는 것은 전달 손실과 비용. 기준은 하나예요 — "사람 팀이라도 쪼갤 일인가?" 아니라면 에이전트 하나 + 좋은 도구가 답입니다.

유혹의 구조

에이전트 하나가 시원찮으면 이런 상상을 하게 됩니다 — "기획 에이전트, 코딩 에이전트, 리뷰 에이전트를 만들어서 서로 협업시키면 되겠다!" 회사 조직도처럼요. 가끔은 맞습니다. 그런데 사람 조직에서 벌어지는 일이 여기서도 똑같이 벌어집니다 — 전달하다 빠지는 맥락, 회의(토큰) 비용, 서로 "그건 쟤 일"이라며 빠뜨리는 구멍.

그래서 출발 질문은 "몇 개로 쪼갤까"가 아니라 "쪼개면 뭘 얻는데?"여야 합니다.

쪼개서 얻는 것 — 정당한 이유 셋

① 컨텍스트 격리. 컨텍스트 윈도우 글에서 봤듯, 책상 하나에 모든 서류를 올리면 가운데가 흐려지고 서로 간섭합니다. 검색 담당은 검색 결과만, 작성 담당은 개요와 근거만 보게 하면 각자의 책상이 깨끗해져요. 긴 작업에서 품질이 갈리는 실제 이유의 대부분이 이것입니다.

② 도구·권한 격리. 조회 도구만 가진 에이전트와 실행 도구를 가진 에이전트를 분리하면, 프롬프트 주입 글의 그 원칙 — "속아도 사고가 안 나게" — 이 구조로 보장됩니다. 읽기 에이전트가 오염돼도 실행 권한이 없으니까요.

③ 병렬성. 서로 독립인 하위 작업(리전별 조사, 문서 10개 요약)은 동시에 돌리면 그냥 빠릅니다.

이 셋 중 어느 것도 해당 없다? 그럼 쪼개서 얻는 건 없고 잃는 것만 남습니다.

잃는 것 — 회의 비용과 전달 손실

에이전트 간 소통은 결국 텍스트 전달입니다. A가 조사한 걸 B에게 넘길 때, 요약하면 정보가 빠지고 통째로 넘기면 토큰이 폭발하죠. 사람 조직의 "보고서 전달 게임"과 정확히 같은 손실 구조입니다. 게다가 단계가 늘수록 어디서 틀렸는지 추적이 어려워지고(디버깅 지옥), 호출 수가 곱으로 늘어 비용·지연도 뜁니다.

경험칙: 파이프라인이 3~4단을 넘어가면, 늘린 지능보다 잃은 맥락이 커지는 경우가 많습니다.

실전 패턴 둘만 알면 된다

① 오케스트레이터 + 작업자. 사장 하나가 일을 쪼개 나눠주고 결과를 취합합니다. 작업자끼리는 서로 대화하지 않아요 — 통신 경로가 별 모양(★)이라 추적이 쉽고, 병렬도 자연스럽습니다. 멀티에이전트의 8할은 이걸로 충분합니다.

오케스트레이터: "리전별 요금을 조사해 표로" 
  ├─ 작업자1: 서울 리전 조사 (동시에)
  ├─ 작업자2: 도쿄 리전 조사 (동시에)
  └─ 취합·검수 후 응답

② 파이프라인. 초안 → 검수 → 수정처럼 순서가 본질인 작업. 각 단계의 입출력 형식을 계약처럼 고정하는 게 요령입니다(자유 산문 전달 금지, 구조화된 형식으로). 단계 사이가 곧 손실 지점이니까요.

에이전트끼리 자유 대화하게 두는 구조(그물형)는 데모에선 신기한데, 운영에선 비용·추적성 양쪽에서 대가가 큽니다. 명확한 근거 없이는 비추천.

판별 체크리스트

□ 하위 작업들이 서로 독립인가 (병렬 이득)          → 예: 쪼갤 후보
□ 단계마다 필요한 컨텍스트·도구가 크게 다른가        → 예: 쪼갤 후보
□ 권한을 구조적으로 분리해야 하는가 (조회/실행)      → 예: 쪼갤 후보
□ 셋 다 아니오                                    → 에이전트 1 + 도구·프롬프트 개선

그리고 순서의 원칙 — 파인튜닝 글의 그 사다리와 같습니다: 프롬프트 개선 → 도구 개선 → 에이전트 하나 잘 만들기 → 그래도 안 되면 분할. "멀티에이전트가 필요해요"의 상당수는 앞 단계에서 해결돼요.

운영 팁 둘

  • 평가는 단계별로. LLM 평가 글의 원칙 그대로 — 전체 결과만 재면 어느 에이전트가 문제인지 모릅니다. 오케스트레이터의 분배, 각 작업자의 산출을 따로 채점하세요.
  • 비용 상한을 전체에. 에이전트 하나의 루프 상한만으론 부족합니다 — 위임이 위임을 부르면 곱으로 뛰니, 전체 작업 단위의 토큰·호출 예산을 거세요.

한 줄 정리

멀티에이전트의 본질은 분업의 이득이 회의 비용을 넘는가입니다. 컨텍스트·권한·병렬 중 하나라도 확실한 이유가 있을 때만 쪼개고, 쪼갠다면 오케스트레이터+작업자부터 — 그리고 언제나 그 전에, 에이전트 하나를 먼저 잘 만들어보세요.
