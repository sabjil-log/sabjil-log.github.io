❯ 로컬 LLM은 언제 정답인가 — 온디바이스 vs API의 손익분기

한 줄 요약: 로컬(자체 서빙) LLM의 손익은 가동률과 규제가 정합니다. 간헐 사용이면 API가 압도적으로 싸고(서버리스 글의 그 택시 논리), 상시 고부하이거나 데이터 반출이 금지된 환경이면 로컬이 답이 됩니다. 그리고 품질·운영 부담은 여전히 API 쪽이 유리하다는 걸 전제로 계산해야 해요.

세 가지 축으로 갈린다

① 데이터 경계 (가장 강한 조건). 공공·금융·의료처럼 데이터를 외부로 못 보내는 환경이면 계산이 끝납니다 — 비용이 비싸도 로컬입니다. CSAP 대상 시스템, 개인정보를 프롬프트에 담아야 하는 워크로드가 여기 해당하죠. 게이트웨이 글의 마스킹·가명화로 완화하는 방법도 있지만, "원문이 필요한 작업"(문서 요약, 상담 이력 분석)은 마스킹으로 품질이 무너지는 경우가 많습니다.

② 가동률. GPU는 켜두면 나가는 비용(상시 서버)이고, API는 부른 만큼(택시)입니다.

자체 서빙: GPU 시간당 요금 × 24 × 30 (또는 카드 감가 + 전기 + 공간)
API:       (입력 토큰 + 출력 토큰) × 단가 × 호출 수

→ 하루 몇 백 건: API가 수십 배 저렴 (GPU는 대부분 유휴)
→ 초당 수십 건 상시: 로컬이 역전하기 시작

여기서 자주 빠뜨리는 게 프롬프트 캐싱입니다 — API는 고정 프리픽스에 큰 할인이 붙으니(그 글의 구조), 시스템 프롬프트가 긴 RAG 서비스라면 API 실효 단가가 계산보다 훨씬 낮아집니다. 손익분기를 재기 전에 캐싱 적용 후의 단가로 계산하세요.

③ 품질·모델 선택권. 최상위 모델은 대개 API로만 제공됩니다. 로컬은 오픈 웨이트 모델의 성능 범위 안에서 골라야 하고 — 다만 작업이 좁으면 그 격차가 무의미해집니다. 분류·추출·정형 요약 같은 일은 중소형 모델이 충분히 하고(구조화 출력 글의 그 스키마 강제까지 붙이면 더), 그런 작업이 대량이면 로컬의 단가 우위가 그대로 실현되죠.

로컬을 택했을 때 실제로 하는 일

"GPU 사서 돌린다"의 실체는 인프라 운영입니다.

  • 서빙 엔진 운영 — vLLM 등으로 API 형태 노출, 동시 요청 배칭, 컨텍스트 한도 관리
  • VRAM 계산 — 양자화 글의 그 산수(가중치 + KV 캐시 + 동시 요청 수). 동시성이 늘면 KV 캐시가 VRAM을 먹으니, "모델은 들어가는데 동시 3명이면 터진다"가 흔한 실패
  • 가용성 — 카드 한 장이면 그게 SPOF입니다. 장애 시 API로 폴백하는 구성(게이트웨이 글의 그 폴백)이 현실적인 절충
  • 업데이트 — 더 좋은 오픈 모델이 나오면 교체·재평가. API는 벤더가 하는 일을 우리가 하는 것

이 운영 부담을 비용에 넣지 않은 비교는 대개 로컬에 유리하게 왜곡됩니다.

하이브리드가 대개 정답

실무에서 자주 안착하는 형태:

[민감 데이터 / 대량 정형 작업]  → 로컬 (자체 서빙)
[복잡한 추론 / 간헐 고난도]     → API
[둘 사이 라우팅·폴백·계측]      → LLM 게이트웨이

게이트웨이 글의 그 관문이 여기서 진짜 값을 합니다 — 앱은 어디로 가는지 모른 채 한 곳에 요청하고, 라우팅 규칙(데이터 등급·작업 유형)으로 로컬/API를 나눕니다. 로컬이 죽으면 API로, 규제 대상 데이터는 절대 API로 안 가게 — 정책을 코드 한 곳에서 집행하는 구조.

결정 절차

1. 데이터 반출이 금지되는가 → 예: 로컬 확정 (아래는 참고만)
2. 캐싱 적용 후 API 월 예상 비용 계산  vs  GPU 월 비용 + 운영 공수
3. 작업 난도가 중소형 모델로 충분한가 → 골든셋으로 실측 (벤치마크 글의 3단 절차)
4. 로컬로 간다면: 동시성 기준 VRAM 계산 + API 폴백 설계

한 줄 정리

로컬 LLM은 규제(반출 금지)이거나 상시 고부하일 때 정답입니다. 그 외에는 캐싱 적용된 API가 대개 싸고 편하고 좋고요 — 결정은 골든셋 실측 + 운영 공수를 포함한 계산으로, 그리고 대부분은 게이트웨이로 둘을 섞는 하이브리드에 안착합니다.
