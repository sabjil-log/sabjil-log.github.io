❯ A, CNAME, MX, TXT — 도메인 연결이 안 될 때 봐야 할 레코드들

한 줄 요약: DNS 레코드는 도메인이라는 이름 아래 달아두는 안내판 모음입니다. A는 "IP는 여기", CNAME은 "쟤랑 같음", MX는 "메일은 이쪽", TXT는 "메모(소유확인·SPF)". 그리고 "변경했는데 반영이 안 돼요"의 범인은 대부분 TTL 캐시입니다.

레코드 = 용도별 안내판

도메인 하나에는 용도가 다른 안내판 여러 장이 붙습니다. 실무에서 만지는 건 사실상 이 네 장 + α예요.

A (Address) — "이 이름의 IP는 1.2.3.4". 가장 기본. 도메인을 서버·LB의 IP에 직결합니다. (IPv6용은 AAAA.)

CNAME (별명) — "www.example.com은 example.com과 같음" 혹은 "shop.example.com은 쇼핑몰 플랫폼의 xxx.hosting.com을 봐라". IP를 직접 적지 않고 다른 이름으로 위임하는 것. 대상의 IP가 바뀌어도 내 레코드는 손댈 필요가 없어서, SaaS·CDN 연결의 표준입니다.

CNAME엔 유명한 제약이 하나 있습니다 — 루트 도메인(example.com 자체)에는 원칙적으로 못 답니다(다른 레코드와 공존 불가 규칙 때문). 그래서 DNS 업체들이 ALIAS/ANAME/플래트닝 같은 우회 기능을 제공하죠. "www는 되는데 루트는 안 돼요"가 이 얘기입니다.

MX (Mail eXchange) — "이 도메인 앞으로 온 메일은 이 서버로". 웹은 A로 우리 서버를 보게 하고, 메일은 MX로 구글 워크스페이스를 보게 — 웹과 메일이 딴 살림을 차릴 수 있는 이유입니다. 숫자(우선순위)는 낮을수록 먼저.

TXT (텍스트 메모) — 자유 텍스트인데 실무에선 두 용도가 지배적입니다. ① 소유 확인 (구글 서치콘솔·각종 SaaS가 "이 값을 TXT로 달아라" 하는 그것 — 우리가 네이버 인증 때 메타태그로 한 걸 DNS로 하는 방식), ② 메일 인증 (SPF/DKIM/DMARC — "이 도메인 명의로 메일 보낼 자격이 있는 서버 목록"). 회사 메일이 스팸함에 처박히는 문제의 8할이 이 TXT 세 종 미비입니다.

그 외 — NS(이 도메인의 안내판을 관리하는 네임서버가 누군지)와 AAAA 정도 알면 충분합니다.

dig로 직접 열람하기

dig +short example.com A          # IP가 뭐로 잡히나
dig +short www.example.com CNAME  # 별명이 어디를 가리키나
dig +short example.com MX         # 메일은 어디로
dig +short example.com TXT        # 소유확인·SPF 확인
dig example.com ANY +noall +answer   # (지원하는 서버에선) 한꺼번에

한 가지 유용한 습관 — 권위 서버에 직접 물어보기:

dig @8.8.8.8 example.com +short        # 구글 리졸버의 캐시 기준
dig @ns1.내네임서버.com example.com +short   # 원본(권위 서버) 기준

두 결과가 다르면? 변경은 됐는데 캐시가 아직 옛날 값인 겁니다. 그게 다음 얘기.

"반영이 안 돼요" — 범인은 TTL

레코드에는 TTL(초)이 붙어 있습니다 — "이 안내판, 한 번 봤으면 이 시간 동안은 다시 안 물어봐도 됨". CDN 캐시 글의 그 유통기한이 DNS에도 똑같이 있는 거죠. TTL이 86400(하루)인 레코드를 바꾸면, 먼저 봐간 리졸버들은 하루 동안 옛 주소를 답합니다. 전파가 느린 게 아니라 약속대로 캐시 중인 겁니다.

그래서 서버 이전 같은 계획 작업의 정석 순서는:

D-1: TTL을 300(5분)으로 미리 낮춤 (기존 TTL이 만료될 시간을 두고)
D-Day: 레코드 변경 → 최대 5분 내 전환
안정화 후: TTL 원복 (캐시 효율)

바꾸고 나서 TTL을 낮추는 건 늦습니다 — 낮추는 것 자체가 옛 TTL만큼 걸려요.

진단 루틴

  1. dig +short 도메인 — 지금 뭐로 풀리나. 아예 안 나오면 레코드 누락이나 NS 문제.
  2. dig @권위서버 vs dig @8.8.8.8 — 원본과 캐시 비교. 다르면 TTL 대기 중.
  3. CNAME 체인 확인 — dig 도메인 +trace 끝부분. 별명이 별명을 가리키다 끊긴 곳이 없는지.
  4. IP는 맞는데 안 열린다 → DNS 무죄. 계층 진단(nc, curl -v)으로 다음 층 수사.

한 줄 정리

A는 주소, CNAME은 별명(루트엔 불가), MX는 우편함, TXT는 소유확인·메일인증 메모. 반영 문제는 고장이 아니라 TTL — 계획 변경은 TTL 먼저 낮추고 하세요. dig 넉 줄이면 도메인 문제의 대부분이 자백합니다.
