❯ 누가 새벽 3시에 보안그룹을 열었나 — 감사 로그 되짚기

한 줄 요약: 감사 로그는 "누가·언제·어디서·무엇을 했는가"의 API 호출 기록입니다. 장애 원인 추적, 보안 사고 포렌식, 컴플라이언스 증적의 세 가지 용도가 전부 여기서 나오죠. 조건은 하나 — 사고 전에 켜져 있고, 원본 계정 밖에 보존돼 있을 것. 사고 후에 켜는 건 늦습니다.

세 가지 질문에 답하는 로그

  • 장애: "ACG 규칙이 바뀌어서 서비스가 죽었는데, 누가 언제 바꿨나?" → 변경 이력
  • 보안: "이 키가 유출된 것 같은데, 그 키로 뭘 했나?" → 자격증명별 활동
  • 컴플라이언스: "관리자 권한 부여가 승인 절차를 거쳤는지 증명하라" → 증적

콘솔의 서비스별 로그(웹서버 액세스 로그 등)와 다릅니다 — 감사 로그는 클라우드 관리 평면(콘솔·CLI·SDK로 한 모든 행위)의 기록이에요. AWS의 CloudTrail, NCP의 Cloud Activity Tracer/감사 로그 계열이 이것. 서버 안에서 벌어진 일(SSH 후 명령)은 여기 없고 배스천·OS 로그의 영역입니다.

켜기 — 그리고 밖으로 내보내기

기본 콘솔 이력은 보존이 짧습니다(수십 일). 그래서 첫 작업은 장기 보존 + 원본 계정 밖 저장:

감사 로그 → 전용 버킷 (별도 보안 계정, pull 방식) → 불변 보존 (오브젝트 락)
                                                   → 로그 중앙화 파이프라인으로 검색 가능하게

크로스 리전 글의 "권한 분리·시간 분리"가 그대로 적용됩니다. 이유는 명확해요 — 침입자가 첫 번째로 하는 일이 로그 삭제입니다. 운영 계정의 admin이 지울 수 있는 곳에 있는 감사 로그는 감사 로그가 아니에요.

그리고 읽기 이벤트까지 켤지 결정합니다. 기본은 쓰기(변경)만 기록하는 경우가 많은데, "누가 이 버킷의 파일을 읽었나"가 필요한 환경(개인정보 저장소)은 데이터 이벤트도 켜야 합니다 — 볼륨과 비용이 커지니 대상 버킷을 골라서.

뒤지는 법 — 세 가지 축

로그 한 줄의 구조는 어디나 비슷합니다: 시각 · 행위자(누가, 어떤 자격증명으로) · 행위(어떤 API) · 대상(어떤 리소스) · 출처(IP, 콘솔/CLI) · 결과(성공/거부).

# 예: AWS CLI로 "보안그룹 변경" 이벤트 찾기
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=AuthorizeSecurityGroupIngress \
  --start-time 2026-09-14T00:00:00Z --query 'Events[].[EventTime,Username,CloudTrailEvent]' --output table

세 가지 추적 축:

① 리소스 → 누가. "이 ACG를 바꾼 사람" — 대상 리소스 ID로 필터. 장애 추적의 기본 동작.

② 자격증명 → 무엇. "이 액세스 키가 지난 24시간에 한 것 전부" — 유출 의심 시 첫 질문. 여기서 평소와 다른 리전, 새벽 시각, 처음 보는 API(예: 갑자기 대량의 인스턴스 생성 — 코인 채굴 패턴)가 보이면 확정입니다. 최소권한 글의 폭발 반경이 실제로 얼마였는지도 이 조회로 나오죠.

③ 거부 이벤트. AccessDenied가 특정 자격증명에서 반복되면 — 권한 부족한 배치(정상)일 수도, 권한 탐색 중인 공격자(비정상)일 수도 있습니다. 어느 쪽이든 봐야 할 신호.

알람으로 승격할 것들

로그는 쌓여 있는 것만으로는 사후 수사 도구입니다. 몇 가지는 실시간 알람으로 올려야 해요 (알람 설계 글의 P1 기준 — 받으면 지금 할 행동이 있는 것):

  • 루트/최고 관리자 계정 사용 (평소엔 쓰면 안 되는 계정 — break-glass 개봉 신호)
  • 감사 로그 설정 변경·중지 시도 (로그를 끄려는 행위 자체가 최고 경보)
  • IAM 정책·관리자 권한 부여
  • 보안그룹/ACG에서 0.0.0.0/0 인바운드 개방
  • 평소 안 쓰는 리전에서의 리소스 생성

컴플라이언스 관점

CSAP·ISMS-P 심사에서 "접근 통제 이력" "권한 변경 승인" 항목은 결국 이 로그를 증적으로 제출하는 일입니다. 심사 때 급히 뒤지는 게 아니라 — 보존 기간(대개 1년 이상 요구)이 정책으로 걸려 있고, 월간 점검에 "관리자 권한 변경 건 검토"가 루틴으로 있으면 심사 대응이 작업이 아니라 출력이 됩니다. 태그 정책 글의 owner 태그가 여기서 "누가 승인했나"의 연락처로 이어지고요.

한 줄 정리

감사 로그는 사고 전에 켜서 밖에(별도 계정·불변 보존) 두는 것이 전부입니다. 뒤질 땐 리소스→누가, 자격증명→무엇, 거부 이벤트 세 축으로, 루트 사용·로그 중지·관리자 부여·0.0.0.0/0 개방은 실시간 알람으로 — 그러면 새벽 3시의 그 변경도, 심사 때의 증적도 검색 한 번입니다.
