❯ LLM 호출을 한 문으로 모아라 — 게이트웨이(릴레이) 패턴

한 줄 요약: LLM 게이트웨이는 모든 LLM 호출이 지나가는 단일 관문입니다. 벤더 API 키는 게이트웨이만 알고, 앱들은 게이트웨이에게만 말하죠. 얻는 것 — 키 통제, 사용량·비용 가시성, 폴백/재시도, 정책(마스킹·차단) 일괄 적용. 배스천이 SSH에 한 일을 LLM 호출에 하는 겁니다.

흩어지면 생기는 일

팀마다 챗봇, 요약기, 에이전트를 만들며 각자 벤더 API를 직접 부릅니다. 반 년 뒤 —

  • 키가 사방에 — 서비스 5개 × 벤더 2곳의 키가 각 저장소·설정에 흩어져, 회수하려면 사냥부터(Secret 글의 그 악몽).
  • "이번 달 LLM 비용 왜 이래?"에 답 못 함 — 어느 서비스가 얼마 썼는지 집계 불가.
  • 벤더 장애 = 전 서비스 장애 — 폴백이 없으니.
  • 정책이 제각각 — 마스킹을 하는 앱과 안 하는 앱이 공존.

배스천 글에서 본 그 문제입니다 — 문이 N개면 지킬 곳도 N개. 처방도 같아요: 문을 하나로.

게이트웨이가 서는 자리

[앱들] --(내부 인증)--> [LLM 게이트웨이] --(벤더 키)--> [벤더 A / 벤더 B / 로컬 모델]

구현 관점에서 핵심은 표준 API 모양을 그대로 흉내 내는 것입니다 — /v1/messages, /v1/chat/completions 같은 표준 엔드포인트를 게이트웨이가 제공하면, 앱들은 base URL만 바꾸면 그대로 붙습니다. 기존 SDK·코드 무수정. (이게 릴레이라 불리는 이유 — 받은 요청을 그대로 벤더에 중계하되, 중간에서 부가가치를 얹는 구조죠.)

게이트웨이가 얹는 부가가치, 우선순위 순으로:

① 키의 단일 보관. 벤더 키는 게이트웨이의 Secret에만. 앱에는 게이트웨이용 내부 토큰을 발급합니다 — 서비스별로 다르게, 회수 가능하게(최소권한 글의 그 원칙). 키 유출 사고의 폭발 반경이 "그 앱의 내부 토큰 하나"로 줄어듭니다.

② 사용량 계측. 모든 요청이 지나가니, 서비스별·모델별 토큰 사용량과 비용이 한 곳에 쌓입니다. usage 응답을 저장하는 것만으로 "이번 달 청구서" 질문이 대시보드 하나로 끝나요. 프롬프트 캐싱 글의 캐시 히트율 지표도 여기서 공짜로 나옵니다.

③ 폴백과 재시도. 벤더 A가 429/5xx면 B로, B도 죽으면 로컬 모델로 — 헬스체크·로드밸런서 글의 그 구도가 LLM 층에서 재현됩니다. 주의 하나: 모델이 바뀌면 답변 품질·형식이 흔들릴 수 있으니, 폴백은 "무조건 투명하게"보다 응답에 어떤 모델이 답했는지 표시하는 게 운영상 정직합니다(평가·디버깅을 위해).

④ 정책의 일괄 적용. 요청이 벤더로 나가기 전에 민감정보 마스킹/가명화(로그 중앙화 글의 그 마스킹이 LLM 방향으로도 필요한 이유 — 프롬프트는 회사 데이터가 외부로 나가는 통로입니다), 금칙 요청 차단, 팀별 레이트리밋·예산 상한. 에이전트 글의 "루프 상한"을 조직 차원으로 올린 셈이죠.

설계 포인트 셋

스트리밍을 처음부터. LLM 응답은 SSE 스트리밍이 기본인데, 게이트웨이가 전체 응답을 모았다 주면 체감 지연이 확 나빠집니다. 통과시키면서 계측(청크를 흘리며 토큰 집계)하는 구조로 — 프록시 구현에서 제일 자주 틀리는 지점입니다.

게이트웨이 자신이 SPOF. 문을 하나로 모으면 그 문이 죽을 때 전부 죽습니다 — 배스천 글의 그 경고 그대로. 게이트웨이는 상태 없는(stateless) 얇은 계층으로 유지하고(계측 기록은 비동기로 밖에), 2대 이상 + LB 뒤에 두세요. 그리고 게이트웨이 우회 금지를 네트워크로 강제 — 벤더 API로 나가는 직접 호출을 이그레스에서 막아야 "선택적 준수"가 안 됩니다.

로깅의 딜레마. 요청·응답 전문을 남기면 디버깅·평가(골든셋 재료!)에 최고지만, 그 로그가 곧 민감정보 저장소가 됩니다. 균형점 — 메타데이터(누가·언제·모델·토큰·지연)는 전부, 본문은 마스킹 후 샘플링 또는 팀별 옵트인.

언제 도입하나

서비스 하나면 과잉입니다. 신호는 명확해요 — LLM을 쓰는 서비스가 2~3개를 넘고, "비용 집계 좀"이나 "키 교체 좀"이 고통이 되기 시작할 때. 자체 구현(FastAPI로 표준 엔드포인트 + 중계)도 하루이틀 거리고, LiteLLM 같은 기성 게이트웨이를 세우는 것도 방법입니다 — 어느 쪽이든 얇게 유지하는 게 요령입니다.

한 줄 정리

LLM 게이트웨이는 LLM 호출의 배스천입니다 — 키는 한 곳에, 비용은 보이게, 장애엔 폴백, 정책은 일괄로. 표준 API 모양을 유지해 앱은 base URL만 바꾸게 하고, 스트리밍 통과·무상태·우회 차단까지 챙기면 — 흩어진 호출들이 관리 가능한 하나의 시스템이 됩니다.
